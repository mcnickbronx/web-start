# Как устроен проект
Техническая заметка для разработчика · 05.10.2026

Django держит схему, миграции и админку, FastAPI отдаёт API мимо Django, Tortoise ORM
даёт асинхронный доступ к тем же таблицам. Ниже — как эти части сложены вместе.

## Как это запускается

Локально всё поднимается одной командой `runserver` — админка и API на одном порту.
На сервере — тот же `project/asgi.py` под uvicorn: в профиле light админка и API одним процессом,
в full админка — отдельным процессом, плюс воркер очереди задач через Redis.

Подробно — в описании [настроек и точек входа](../app/project/readme.md).

## Путь запроса

Запросы разделяются до того, как их увидит Django: всё, что начинается с `/api`, уходит
в FastAPI, остальное — в админку. Поэтому в API не работает ничего из привычного Django:
ни сессии, ни CSRF, ни его проверка прав. Авторизация в API своя, на токенах.

Дальше запрос проходит четыре шага: проверка, что домен вправе обращаться к API;
поиск нужного эндпоинта; проверка присланных данных по схеме; проверка токена, если
эндпоинт требует авторизации. Только после этого начинает работать наш код, и почти
всегда это один вызов функции из `services.py`. Ответ собирается по схеме ответа —
наружу уходят только перечисленные в ней поля, случайно отдать лишнее нельзя.

По файлам (от `app/`) — на примере `GET /api/page/list`:

1. `project/asgi.py` — `/api/*` уходит в FastAPI, остальное — в Django.
2. `project/api.py` — сборка FastAPI: домены (CORS), единый формат ошибок, роутер каждого
   модуля на `/api/<модуль>/`.
3. `page/rest.py` — эндпоинт: параметры запроса, схема ответа, вызов сервиса.
4. `page/services.py` — логика и запрос к базе через Tortoise-модели из `page/models_async.py`.
5. Ответ проверяется по схеме из `page/schemas.py`; формат списка и ошибок — общий, из `core`.

## Зачем две ORM

Django владеет схемой: модели, миграции, админка. Но его способ ходить в базу
синхронный, а API должен обслуживать сотни одновременных запросов, поэтому в API
работает асинхронная Tortoise ORM.

Чтобы схему не описывать дважды, модели для API генерируются из моделей Django
командой `sync_async_models`. Django остаётся единственным источником правды,
а сгенерированные файлы лежат в git, и на деплое проверяется, что они не отстали.
В коммит идут оба файла — миграция и `models_async.py`.

В API модели ведут себя как в Django: обратная связь называется так же
(`category.product_set` или свой `related_name`), ссылка на модель — `"models.Product"`.
Связь на модель вне проекта (`auth.Group`) в API — просто колонка `group_id`: генерируются
только модели самого проекта.

Отсюда два следствия, о которых легко забыть:

- логику нельзя класть в `save()` и сигналы — из API они не вызываются;
- в API нельзя обращаться к базе способом Django — он заблокирует процесс, и проверка
  внутри Django этого не позволит.

Общее место для логики — `services.py` модуля. Его зовут и API, и админка, и команды.
Сервис с базой пишется асинхронным, а синхронные админка и команды вызывают его через
мост из `core` — один код на обе стороны, см. [ядро](../app/core/readme.md).

## Что легко сломать

- Забыть `sync_async_models` после изменения моделей: локально API будет работать
  со старой схемой, а деплой остановится на проверке.
- Удалить из API запись, у которой есть связанные: правило удаления по умолчанию
  живёт в Django, а не в базе. Нужно удалять из API — объявляйте связь через `DB_CASCADE`.
- Назвать модель так же, как в другом модуле: для API все модели лежат в одном
  пространстве имён, имена должны быть уникальными.
- Сделать в эндпоинте что-то долгое и синхронное — запрос по сети, отправку письма,
  тяжёлый расчёт. Встанет весь процесс, а не один запрос. Такое место — фоновой задаче.
- Написать эндпоинт обычной функцией или через синхронный ORM. FastAPI выполнит его
  в пуле потоков, и API будет держать столько же пользователей, сколько Django: на замере
  синхронный FastAPI — ~300 активных на ядро, асинхронный — ~700. Выигрыш шаблона даёт
  асинхронный код, а не FastAPI сам по себе (см. [benchmark.md](benchmark.md)).
- Ходить во внешние API через `httpx` из асинхронного кода: с сотен одновременных вызовов
  он упирается в процессор (66 запросов в секунду против 600 у `aiohttp` на том же ядре).
- Показать в списке связанные объекты и забыть про их предзагрузку: получится
  отдельный запрос к базе на каждую строку.
