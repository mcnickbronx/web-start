# Бэкенд web-start

Стартовый шаблон: **Django** — модели, миграции, админка; **FastAPI** — API.

Админка и API — один код и одна точка входа. Запросы делятся до Django: `/api/*` обрабатывает
FastAPI, middleware Django в API не участвуют.

## Зачем он нужен

Шаблон для проектов с личным кабинетом. Страница такого кабинета делает под полтора
десятка запросов к API, и синхронный стек упирается в соединения и память раньше,
чем в процессор.

Отсюда разделение. Django оставлен ради админки и миграций — писать их заново дороже,
чем держать вторую ORM. API вынесен мимо Django целиком, чтобы запрос не проходил его
middleware. Доступ к базе из API сделан по-настоящему асинхронным, а не «асинхронным
снаружи».

## Структура

```
app/
├── manage.py
├── project/
│   ├── settings.py          # общие настройки Django и API; окружение — из .env (шаблон: .env.txt)
│   ├── api.py               # сборка FastAPI: роутеры из */rest.py, Swagger, ошибки
│   ├── asgi.py              # админка + API: локально (runserver) и на сервере; в full админка — своим процессом
│   ├── worker.py            # прод: воркер очереди задач
│   ├── crontab              # задачи по расписанию: уборка модулей и свои (сервис cron)
│   └── urls.py              # /admin
├── core/                    # общее: ошибки, списки, Tortoise, генератор моделей, задачи, runserver
├── log/                     # модуль «Журнал»: логи в БД, админка только на чтение
├── user/                    # модуль «Пользователи»: JWT, /api/user/*
├── page/                    # необязательный модуль «Страницы»: страницы, блог, SEO, sitemap
├── form/                    # необязательный модуль «Заявки»: формы сайта, капча, файлы
└── live/                    # необязательный модуль «Живые события»: WebSocket, событие пользователю
```

Какую нужду закрывает каждый модуль и что из общего есть в `core` — [карта модулей](../readme.md#из-чего-собирается-проект).

`project` — настройки и точки входа, то есть какой это проект и как он запускается.
`core` — общее для всех модулей: ошибки, пагинация, генератор моделей, задачи, письма.
Переиспользуемое кладём в `core`, настройку проекта — в `project`.

Исключение — команды `manage.py`: Django ищет их только в приложениях из `INSTALLED_APPS`,
а `project` приложением не является. Поэтому свой `runserver` лежит в `core`, рядом
с `sync_async_models`. `core` стоит в списке первым — иначе его `runserver` не перекроет
стандартный.

Как это работает вместе — [docs/architecture.md](docs/architecture.md).

## Локальный запуск

```bash
python3 -m venv .venv
. .venv/bin/activate
pip install -r requirements.txt

cp .env.txt .env        # DEV=True, заполнить DEV_DB_* — свою локальную базу
createdb project

cd app
python manage.py migrate
python manage.py sync_async_models
python manage.py createsuperuser
python manage.py runserver
```

- Админка: http://127.0.0.1:8000/admin/
- Swagger: http://127.0.0.1:8000/api/docs

Python 3.14, база — PostgreSQL.

## Модуль

Модуль — обычное Django-приложение из `INSTALLED_APPS`:

```
app/<module>/
├── apps.py        # verbose_name — название раздела в админке и в Swagger
├── models.py      # Django-модели → миграции
├── admin.py       # админка
├── models_async.py   # Tortoise-модели для API — генерируются, руками не править
├── schemas.py     # Pydantic-схемы запросов и ответов (*In / *Out)
├── services.py    # логика; эндпоинты и задачи вызывают её
├── rest.py        # router = APIRouter() → /api/<module>/...
└── tests/         # тесты, хелперы в tests/create.py
```

`rest.py` подключается автоматически, регистрировать роутер не нужно.

Новый модуль — по шагам, из `app/`:

1. `python manage.py startapp <module> --template=core/module_template` — папка со всеми файлами
   модуля, `tests/` и заготовкой `readme.md`. Главное в ней — `tests/__init__.py`: без него Django
   не находит тесты модуля и молча их пропускает.
2. В `apps.py` — `verbose_name` по-русски: так модуль называется в админке и в Swagger.
3. Модуль — строкой в `INSTALLED_APPS` (`project/settings.py`).
4. Модели → `makemigrations` → `sync_async_models` → `migrate`, админка — в `admin.py`.
5. `schemas.py`, `services.py`, `rest.py` — эндпоинты появятся на `/api/<module>/`. Поменялось
   API — `npm run api:types` во `front/`: [типы API для фронта](docs/commands.md#типы-api-для-фронта).
6. Тесты — `tests/test_<фича>.py`, хелперы создания объектов — `tests/create.py`; как писать —
   [правила тестов](CLAUDE.md#тесты), запуск — `python manage.py test <module> --keepdb`.
7. `readme.md` модуля — в том же коммите, строкой в оглавление ниже и в [карту модулей](../readme.md#из-чего-собирается-проект).
   Что почувствуют сайты — строкой в `CHANGELOG.md`, по [правилу репозитория](../CLAUDE.md).

## Почему так, а не иначе

Выбор по каждому куску стека — чтобы не переделывать его по второму разу.

| Вопрос | Решение | Почему |
|---|---|---|
| Админка | Django | sqladmin (0.32, 09.2026): нет inline, загрузки файлов, групп и прав |
| Вид админки | стандартный Django | тема Unfold — по желанию проекта: [docs/unfold.md](docs/unfold.md) |
| Фильтры списков в админке | свой пакет [django-admin-filter-kit](https://github.com/mcnickbronx/django-admin-filter-kit) | фильтр с подсказками на встроенном автокомплите Django, сворачиваемая панель и курсор в поиске подсказок; `django-admin-autocomplete-filter` заброшен с 2021 и в Django 6 падал |
| Выгрузка списков в Excel | `openpyxl`, xlsx | у ячейки свой тип: текст посетителя не станет формулой, `+7…` — числом; в CSV то и другое угадывает Excel |
| Миграции | Django, по модулям | источник схемы один |
| API | FastAPI на уровне ASGI, до Django | middleware Django в API не участвуют |
| Доступ к БД из API | Tortoise ORM + asyncpg | честный async; Django ORM async и Django Ninja внутри синхронны |
| Не Django + Ninja или DRF | замер, [benchmark.md](docs/benchmark.md) | под нагрузкой страница вдвое быстрее, с внешними вызовами — в 3–4 раза; на одном ядре больше запросов, чем Django на двух |
| Модели для API | генерируются из Django-моделей | схема одна, дублировать руками нельзя |
| Генератор | свой, `core/generator.py` | у `django-tortoise-objects` нет `auto_now` и callable-дефолтов |
| Авторизация | своя JWT | перенесена из старого шаблона с исправлениями |
| Пароли | хешеры Django | пароль из админки работает в API и наоборот |
| Фоновые задачи | taskiq | у `django.tasks` из Django 6 пока только dummy и immediate бэкенды |
| Django | 6.1 | ради `DB_CASCADE`: каскад уходит в базу, и удаление из API работает |
| Python | 3.14 | весь стек на нём проверен |
| Зависимости | точные версии в `requirements.txt` | сборка образа не зависит от даты |
| Журнал логов | свой модуль `log`, запись через очередь | `django-db-logger` пишет синхронно и не попадает в генерацию `models_async.py` |

Версии пакетов зафиксированы точно, в [requirements.txt](requirements.txt): Django 6.1,
FastAPI 0.141, Tortoise ORM 1.1, taskiq 0.12. Python 3.14, база — PostgreSQL, проверено на 17.

FastAPI ещё не дошёл до 1.0, и ломающие изменения у него случаются в минорных версиях.
Обновлять его стоит отдельным заходом и с проверкой, а не заодно с остальными пакетами.

## Деплой

Коротко: push в `dev` или `main` — CI гоняет тесты и собирает образ. Сервер выкладывает тот,
что указан в его `.env` (миграции, статика, проверка здоровья; при сбое остаётся прежняя версия):
dev-проект идёт за веткой `dev` сам, сайт стоит на версии (`:v3.0.0` или хеш коммита) и обновляется её сменой. На сервере —
`docker compose ps`, `docker compose logs` в папке проекта. Подробно — [docs/deploy.md](docs/deploy.md).
