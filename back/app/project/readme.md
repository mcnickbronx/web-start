# Настройки и точки входа
Как устроен `project` · 05.10.2026

`project` отвечает на два вопроса: какой это проект и как он запускается. Здесь
настройки, точки входа и корневые адреса админки — и больше ничего: логики тут нет,
общий для модулей код лежит в [core](../core/readme.md).

Приложением Django `project` не является: его нет в `INSTALLED_APPS` и у него нет
`apps.py`. Отсюда неочевидное следствие — команды `manage.py` сюда положить нельзя,
Django ищет их только в приложениях. Поэтому свой `runserver` живёт в `core`.

## Как запускается

Код один, а запускается он по-разному — в зависимости от того, что должно работать.

| Точка входа | Когда работает | Что поднимает |
|---|---|---|
| `asgi.py` | локально через `manage.py runserver`, на сервере под uvicorn | админку и API; в профиле full админка — своим процессом с этой же точкой входа |
| `worker.py` | на сервере в профиле full, когда задан `REDIS_URL` | воркер очереди задач |

**Админка и API — одна точка входа, `asgi.py`.** Запросы делятся до Django: всё, что начинается с `/api`,
уходит в FastAPI и middleware Django не проходит. Синхронный код админки выполняется в отдельном
потоке и асинхронный API не останавливает. Локально это удобно: админка по `/admin/`, Swagger
по `/api/docs`, одно окно терминала. На сервере запускается то же самое — проверенное локально.

**Сколько процессов — решает профиль** (`compose.yml`, [deploy.md](../../docs/deploy.md)):

- **light** — админка и API одним процессом. Для контентного сайта: админкой пользуются редко
  и легко, а памяти нужно втрое меньше.
- **full** — админка отдельным процессом, контейнер `admin` с той же точкой входа: Traefik
  отправляет туда `/admin`. Для кабинетов и магазинов, где менеджеры весь день работают
  в админке: тяжёлая выгрузка не тормозит API, нехватка памяти в админке роняет только её,
  у админки своё число процессов (`ADMIN_WORKERS`) и её можно перезапускать отдельно.

Зависший запрос админки приложение само не обрывает: он держит свой поток, пока не завершится.
Поэтому у внешних вызовов всегда `timeout=60`.

**Воркер** нужен, только когда задачи уходят в Redis. Без `REDIS_URL` они выполняются
прямо в процессе API, и отдельный процесс не запускается. Подробности — в описании
[ядра](../core/readme.md).

## Как собирается API

Роутеры подключаются сами. Если в модуле есть `rest.py`, он окажется в API по адресу
`/api/<модуль>/...`, а раздел в Swagger будет называться так же, как раздел в админке —
по `verbose_name` из `apps.py`. Новый модуль с API достаточно добавить в `INSTALLED_APPS`,
регистрировать ничего не нужно.

Адреса документации: `/api/docs` — Swagger, `/api/redoc` — тот же справочник в другом
виде, `/api/openapi.json` — машинное описание, его можно скормить генератору клиента
или другому инструменту.

Есть `/api/health` для внешних проверок доступности. Он отвечает, жив ли HTTP-стек,
и **не проверяет ни базу, ни Redis**: зелёный ответ не означает, что приложение
полностью работоспособно.

Домены, которым браузер разрешает обращаться к API, перечисляются в настройке
`CORS_ALLOWED_ORIGINS`. Забытый домен фронта выглядит как «запрос не доходит»,
хотя API работает — ошибку видно только в консоли браузера.

## Настройки

Настройки разложены на два файла. В `settings.py` — то, что одинаково везде и лежит
в git. В `.env` в корне проекта — значения окружения: ключи, база, домены, почта,
а заодно параметры docker compose (порты, число процессов). У каждого окружения свой
`.env`: у разработчика, на dev-сервере, на проде. В git он не попадает, шаблон
с комментариями — `.env.txt`.

Без `.env` или без обязательной строки в нём проект не стартует и называет, чего
не хватает. Это сделано нарочно: молча подставленные дефолты в таком месте — худший
вариант. Значение по умолчанию есть только там, где оно безопасно: `DEBUG` выключен,
очередь задач без Redis, у почты обычный порт, пул соединений API — 10.

**Две базы и переключатель.** В `.env` две базы: прод (`DB_NAME`, `DB_USER`, `DB_PASSWORD`,
`DB_HOST`, `DB_PORT`) и dev (те же имена с приставкой `DEV_`), а `DEV` выбирает, какую
взять. Dev-база может жить в другом проекте сервера — там, где проверяют перед продом.
Всё о базе видно в одном файле, отдельного файла для приложения нет.

Как это устроено и почему:
- **`DEV` обязателен.** Забытая строка не должна молча увести приложение в прод,
  поэтому без неё проект не стартует.
- **Читается только выбранная база.** На ноутбуке с `DEV=True` прод можно оставить
  пустым — так пароль прода не лежит у каждого разработчика. Выбранная база заполнена
  не полностью — проект не стартует и называет пустые поля.
- **`DEV` отдельно от `DEBUG`.** Включённая для разбора ошибки отладка на проде не должна
  переключать базу.
- **Каждое значение — отдельной строкой, пароль — как есть,** без кодирования
  спецсимволов. Исключение одно: пароль с `$` — в одинарных кавычках (см. `.env.txt`).
- **Адрес базы зависит от того, где запущено приложение:** из контейнера на сервере —
  адрес сервера в сети проекта, с ноутбука — через SSH-туннель. Поэтому `.env` на
  сервере и на ноутбуке всё равно разные.
- **Пароль базы задаёт сервер.** В `.env` его кладёт администратор сервера под этими же
  именами `DB_*`, для dev — с приставкой `DEV_` (`docs/deploy.md`, «Первый запуск»).
  Администратор сменил пароль — его нужно обновить в `.env`, иначе приложение не подключится.

Настройки общие для админки и API: обе половины читают одни и те же значения,
разъехаться им негде.

О чём стоит знать заранее:

- **`JWT_SECRET_KEY` отдельный от `SECRET_KEY`.** Смена одного не разлогинивает другое.
- **`API_DB_POOL_SIZE`** — размер пула соединений на один процесс API. Число процессов,
  умноженное на размер пула, не должно превышать `max_connections` PostgreSQL.
- **`REDIS_URL` пустой** — задачи выполняются в процессе API, Redis и воркер не нужны.
  Так и задумано для локальной работы.
- **`SITE_URL` и `SITE_NAME`** подставляются в письма. Ссылки в письме берут домен
  отсюда, а не из запроса.
- **Локально письма печатаются в консоль** — почтовый ящик для разработки не нужен.
- **С выключенным `DEBUG` куки уходят только по HTTPS.** На сервере сайт открывается
  по HTTPS, иначе вход в админку не сработает: браузер не вернёт куку CSRF. Локально
  с `DEBUG=True` всё работает по HTTP.
- **Комментарий в `.env` — только отдельной строкой.** Локально файл читает Django,
  на сервере — docker compose, и `#` в конце строки они понимают по-разному: Django
  считает его частью значения.
- **Настройки модулей** (сроки входа и кодов, форма заявок, картинки, журнал) — тоже в `.env`, с префиксом
  модуля: см. [как устроено](../core/readme.md#настройки-модулей) и readme модуля.

## Шпаргалка

- Локально — `manage.py runserver`: админка и API на одном порту.
- Админка и API — `asgi.py`, воркер задач — `worker.py`. light — админка и API одним процессом, full — админка отдельно, плюс воркер.
- Новый модуль с API — добавить в `INSTALLED_APPS`, роутер подключится сам.
- Настройки окружения — `.env` в корне, шаблон `.env.txt`. База: `DEV=True` — dev, `DEV=False` — прод.
- `/api/health` говорит только про HTTP, базу он не проверяет.
