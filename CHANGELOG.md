# Изменения по версиям

Что нового в каждой версии `web-start` и что сделать сайту при обновлении — на сервере
бэкенда и в репозитории сайта. Как устроены версии — в [readme](readme.md#версии).
Сверху — самые новые.

## Не выпущено

**Фронт**
- Кабинет на сайте: слой `user` подключается второй строкой `extends` из git, с тем же тегом, что у движка,
  и без `install` — в таблице «Что сайт может поменять» (`front/readme.md`) и в readme слоя; экраны — копия
  образца из `.playground`. Сайтам без кабинета ничего делать не нужно.

## 2.4.0 — 22.10.2026

Сайту: сначала бэкенд — `DEPLOY_IMAGE` на хеш коммита `v2.4.0`, **есть миграция** `form.0007`
(автовыкладка накатит её сама); потом фронт — `extends` на `#v2.4.0`, версии `nuxt`, `vue`,
`vue-router` — как в `front/package.json` движка.

**Фронт**
- Nuxt 4.6.2, Vue 3.5.44, vue-router 5.4.0 (были 4.5.2, 3.5.43, 5.3.1): закрыты критичные уязвимости
  в инструментах разработки — `simple-git` уходит вместе со старым `@nuxt/devtools`, свежий `shell-quote`
  приносит новый `npm install`. На работающий сайт они не попадали: devtools в движке выключены и в сборку
  не входят, так что обновление не срочное. Сайту при переходе на эту версию — те же три версии в своём
  `package.json`, `npm install`, потом `npm audit --omit=dev`: критичных уязвимостей быть не должно.
- Nuxt 4.6 просит Node 24.15 или новее (из 22-й ветки — 22.22.3): в образе `node:24-alpine` уже 24.22,
  локально — обновить Node, иначе `npm install` выдаёт предупреждения `EBADENGINE`.
- Сайт: canonical и Open Graph (`og:url`, `og:type`, `og:locale`) на каждой странице — адрес без параметров,
  `?utm_source=…` и `yclid` — та же страница; страницы из админки задают своё, как раньше. Сайту ничего делать
  не нужно, если на сервере задан `NUXT_PUBLIC_SITE_URL`, иначе адрес берётся из запроса; `siteUrl` теперь
  объявлен в слое `core`, переменная та же.

  Миграций нет, сайту ничего делать не нужно. Проекту на движке — `export_xlsx` в `actions` своей админки.
- Админка: фильтр «Форма» в заявках, сворачиваемая панель фильтров и курсор в поиске подсказок
  на странице записи — из пакета
  [`django-admin-filter-kit`](https://pypi.org/project/django-admin-filter-kit/) 0.3.0 вместо
  `django-admin-autocomplete-filter` и своего кода в `core` (`core/static/core/admin.js` и
  `core/templates/admin/base_site.html` удалены). Для того, кто работает в админке, всё
  как было; свёрнута ли панель, браузер запомнит заново. Миграций нет, сайту ничего делать не нужно.
- Проекту на движке со своими фильтрами из `core.admin_filters` (файла больше нет) — фильтр
  `admin_filter_kit.filters.AutocompleteFilter`: `list_filter = [("поле", AutocompleteFilter)]`,
  `field_name` не нужен, свой заголовок — подклассом с `title`.
- Ядро: слаг из текста — `core.slug.slugify_text` (был в `page.services`): тот же транслит
  для адресов любого модуля. Сайтам ничего делать не нужно; импорт из `page.services` работает по-прежнему.
- Настройки модулей — в `.env` со значениями по умолчанию: сроки входа и кодов (`USER_*`), форма заявок —
  срок, ловушка по времени, форматы, размер и уборка файлов (`FORM_*`), картинки страниц (`PAGE_*`),
  срок хранения журнала (`LOG_KEEP_DAYS`, расписание вызывает `clear_log` без `--days`).
  Список — в `.env.txt` и в readme модулей. Без новых строк всё как было, сайту ничего делать не нужно.
  Своё значение — строка в `.env` бэкенда и пересоздать контейнеры; неверное значение остановит запуск.
  Что действует на сервере — `docker compose exec app python manage.py env_settings` (в профиле full — `app-full`).
- Ядро: файл от посетителя — `core.upload`: проверка формата, пустого файла и размера, случайное имя на диске,
  уборка неприложенных. Первая на нём — форма заявок, для сайта всё как было: те же ошибки 406 и в том же порядке.

- Django 6.1.2, PyJWT 2.15.1 и aiohttp 3.14.4 — выпуски с исправлениями безопасности. Миграций нет, настройки те же.
- Админка страниц: картинка, вставленная в текст редактора, проверяется, как в «Картинках»: файл, который
  не открывается как картинка, — ошибка «Загрузите правильное изображение», а не битая картинка в тексте.
  Миграций нет, сайту ничего делать не нужно.

  редактор загружает в админке страниц. Мажорная версия, но то, что в ней убрано или изменено, движок не использует.
  Миграций нет, настройки те же, сайту ничего делать не нужно. Проекту на движке со своим кодом на Pillow — сверить

- Ядро: заготовка нового модуля — `python manage.py startapp <модуль> --template=core/module_template`

- Тесты: заголовок с токеном — `auth_header(user)` из `user.tests.create` вместо `self.auth(user)`

- Ядро: история изменений — кто, когда и что поменял в записи, было → стало (`core.history`, `core.history_admin`).

  заявку, у которой уже есть история, не удалить — ошибка в админке; откат с удалением таблицы —

  таблица `<Модель>History(HistoryModel)` в модуле и `HistoryAdmin` с `history_fields`, подробно —
  `back/app/core/readme.md`, «История изменений».
- Ядро: история изменений — страница записи не падает, если поле из истории удалили или переименовали; блок

## 2.0.0 — 09.10.2026

Мажорная: из API убраны и переименованы эндпоинты и поля, у фронта изменился «договор» с сайтом.
Сайту на 1.x — шаги из пунктов ниже: про индексацию, cookie, `/blog` в карте сайта, кабинет, `.env` сервера.

**Фронт**
- Слой `page`: старый адрес — постоянный редирект на новый, с теми же параметрами. Список — в админке,
  «Страницы → Редиректы»; сменили слаг опубликованной страницы или рубрики — старый адрес записывается
  сам. Срабатывает при открытии адреса: поисковик, закладка, ссылка извне. Переход по `NuxtLink`
  на старый адрес — по-прежнему 404, такие ссылки правят в коде сайта. Нужен бэкенд той же версии.
- Слой `page`: данные страниц при рендере на сервере — через кэш (`usePageApi()`, маршрут
  `/_page-api/…`): минута свежести, дальше сохранённое сразу и свежее в фоне. Запросы всех
  посетителей больше не упираются в лимит Traefik на IP сервера сайта, бэкенд разгружен,
  упавший бэкенд — сайт на последних данных. Правка в админке — на сайте в пределах минуты,
  в том числе снятие с публикации: на коммитах движка с кэшем до этого снятая статья
  оставалась на сайте до перезапуска.
- Слой `page`: несуществующая страница ленты (`?page=9999`) — 404, а не пустая страница с 200.
  Лента `/blog` без единой статьи — тоже 404: на сайте без блога пустой `/blog` попадал в поиск.
- Слой `page`: canonical ленты и рубрик — без меток рекламы и других параметров, кроме `?page=N`.
- Слой `page`: редирект со старого адреса статьи сохраняет параметры. Раньше метки рекламы (`utm_*`,
  `yclid`, `gclid`) терялись, и заявка с рекламы записывалась как пришедшая из поиска или по ссылке.
- Слой `page`, безопасность: прокси `/media` пересылает только картинки — раньше путь вида
  `/media/%2e%2e/…` уводил к любому адресу бэкенда, API и админке. Кэш данных страниц —
  не больше 1000 ответов, параметры, которых API не знает, отбрасываются: перебором адресов
  больше не раздуть память сервера сайта.
- Слой `page`: `robots.txt` и переключатель индексации `NUXT_PUBLIC_SITE_INDEXED`. **По умолчанию
  сайт закрыт от поиска** (robots.txt — запрет, на ответах noindex): уже открытому сайту при
  обновлении — `NUXT_PUBLIC_SITE_INDEXED=true` в `.env`. Открытый — базовый robots.txt со
  служебными адресами, склейкой меток рекламы и картой сайта. Свой `noindex` в `routeRules`
  сайта больше не нужен.
- Слой `core`: счётчик Метрики — по новому коду из кабинета: `tag.js?id=<номер>`, электронная
  коммерция (`dataLayer`), адрес и источник перехода при запуске. Сайту ничего делать не нужно.
- Слой `core`: уведомление о cookie внизу экрана (`CookieNotice`), по умолчанию включено:
  «Принять» / «Отклонить», отказ выключает Метрику.
  Сайту — ссылка на свою политику: `cookieNotice.policyUrl` в `app.config`; не нужно — `isEnabled: false`.
- Слой `page`: страницы фронта в `sitemap.xml` — из `page.sitemapPageList` в `app.config` сайта
  (в движке — только `/`). Свои публичные страницы сайт дописывает туда: список сайта
  добавляется к списку движка, а не заменяет его. **Сайту с блогом** — дописать `'/blog'`,
  иначе лента пропадёт из карты сайта. Адрес, который есть и у фронта, и в админке, — одна запись.
- Слой `form`: новый токен формы — по коду ответа (406 или ошибка в поле `captcha`), а не по тексту
  ошибки; паузу перед отправкой (ловушка по времени) сообщает бэкенд — `fill_seconds_min`
  в описании формы. Всё внутри `useSiteForm`, сайту ничего делать не нужно.
- Слой `form`: `useSiteForm` грузит форму сам, когда компонент появился в браузере, — строка
  `onMounted(form.load)` в сайте больше не нужна (оставленная — лишний запрос, не ошибка).
  Новое: `form.clearFieldError(name)` на ввод в поле — его подсветка гаснет, пока его исправляют;
  «Укажите телефон или email» — сразу на обоих полях. Своя логика скрытия ошибок в сайте — заменить.
- Слой `form`: заявка ушла, а форма заново не загрузилась (сеть, выкладка бэкенда) — остаётся прежняя
  форма с «Заявка отправлена». Раньше посетитель навсегда видел «Загрузка формы…».
- Слой `user`: вход, активация и пароли — из браузера прямо в API, refresh в куку `httpOnly` кладёт
  сам бэкенд. Серверных маршрутов `/auth/*` больше нет: лимит Traefik на вход считается по адресу
  посетителя, а не один на всех. `useApi()` ходит в API с куками бэкенда (`credentials: 'include'`).
  Из `core` убран `apiErrorFromFetch` — он был нужен только этим маршрутам. Сайту с кабинетом:
  бэкенд — на поддомене сайта (`back.site.ru`), иначе браузер не пришлёт куку.
- Слой `user`: выход срабатывает сразу, на всех устройствах — `logoutAll()`, где я вошёл —
  `sessionList()`, выйти на другом устройстве — `endSession(id)`. Пример — профиль в демо-сайте.
- Слой `user`: `logout()`, как и `logoutAll()`, при сбое бэкенда вход не сбрасывает и возвращает
  ошибку — куку refresh стирает только бэкенд. Раньше вкладка «выходила», а кука оставалась, и следующий
  на том же компьютере входил в кабинет по ней. Сайту с кабинетом — показать ошибку выхода, образец —
  `layouts/lk.vue` демо-сайта.
- Движок больше не запускает `nuxt prepare` своего демо-сайта при установке — сборка сайта быстрее.
  Правило: версии `nuxt`, `vue`, `vue-router` у сайта — как в `package.json` движка.
- «Договор» движка с сайтом — то, что описано в readme слоёв; функции `utils` — внутреннее.
- Слой `page`: у ленты свой тип — `PageFeedList`. Схема списка с пагинацией в API теперь называется
  `ListOut`, а не `Page` (не спутать со страницами сайта), и `Page_PageListOut_` из `api.d.ts` пропал.
  Сайту, который перекрыл `PageBlog` или `PageFeed`, — тип свойства `result` в своём компоненте
  заменить на `PageFeedList`: при следующих переименованиях в API он останется прежним.
- Слой `user`: правило «кабинет `/lk/**` рендерится только в браузере» — в самом слое. Своё `routeRules`
  для `/lk/**` сайту больше не нужно, оставленное ничему не мешает.
- `FormSmartCaptcha`: `sitekey` можно передать прямо из описания формы — `detail.captcha_client_key`, без `?? ''`.
- Сайту делать ничего не нужно, кроме строк про индексацию, cookie, `/blog` в карте сайта, типа ленты
  в перекрытых компонентах и ошибки выхода в кабинете.
  Перекрыл страницу слоя у себя — данные в ней брать как в движке:
  `usePageRequest(key, api => api.GET('/api/page/…'))`, он ходит через кэш.

**Бэкенд**
- Модуль `page`: редиректы — раздел «Редиректы» в админке и `GET /api/page/redirect?path=…`; при смене
  слага опубликованной страницы или видимой рубрики старый адрес записывается сам. Есть миграция.
- Задачи по расписанию — как в обычном cron: файл `project/crontab`, его выполняет сервис `cron`
  (supercronic), вывод — в `docker compose logs cron`. Уборка журнала и ничьих файлов форм — в 04:00
  и 04:30, а не после каждой выкладки. Свои задачи, дописанные в `command` сервиса `cron`, — перенести
  строками в `project/crontab`. Подробнее — `docs/deploy.md`, «Задачи по расписанию».
- Модуль `user`: ошибка про поле — 422 у этого поля, как в модуле `form`: неверный или занятый email,
  слабый пароль, неверный код, неверный текущий пароль; «Пароли не совпадают» — у поля «ещё раз»,
  а не `body`. 406 остался для остального: код уже отправлен, попытки кончились, срок кода истёк,
  аккаунт уже активирован. Сайту ничего делать не нужно: `message` прежний, ошибки по полям — в `fieldMap`.
- Модуль `user`: поля кода из письма — `confirmation_code…` вместо `activation_code…`: код один
  на активацию и на сброс пароля. **Есть миграция** (`user`, колонки переименовываются): пока выкладка
  не сменила контейнеры, прежний код несколько секунд ищет старые колонки — вход и админка в эти
  секунды отвечают ошибкой.
- Модуль `page`: в админке слаг больше не подставляется на лету из заголовка — пустой собирается
  при сохранении, по одному правилу транслита, занятый адрес получает `-2`. Раньше подсказка админки
  и сервер переводили буквы по-разному: «й» — `j` и `y`. Готовые адреса не меняются.
- Модуль `page`: фото с телефона больше не ложится на бок — при загрузке учитывается поворот из EXIF.
  Загруженные раньше так и остались: перевёрнутое — загрузить заново.
- Списки: при равных значениях сортировки — по `id`, новые первыми. Раньше статьи с одной датой
  публикации на границе страниц ленты то повторялись, то пропадали. `sort=--title` — 406, а не 500.
- Списки: номер страницы `page` — не больше 10 000, дальше — 422. Раньше огромный номер
  (`?page=100000000000000000000`) ронял запрос в базе: 500 и ошибка в журнале, на сайте — страница 500.
- **Автовыкладка.** Push в `dev` или `main` — CI (`.github/workflows/back.yml`) гоняет проверки
  и тесты на Postgres 17, собирает образ с кодом и `compose.yml` в `ghcr.io/<владелец>/web-start-back`
  под именем ветки и полным хешем коммита. Сервер выкладывает образ из `DEPLOY_IMAGE` сам: dev-проект
  идёт за `:dev`, боевой стоит на `:<хеш>` и переходит на новую версию, только когда хеш сменят, —
  тот же, что в `extends` фронта сайта. Выкладка: сервис `deploy` (модели для API, миграции, статика), запуск с проверкой
  `/api/health`, при сбое — прежняя версия. Код — в образе и принадлежит root: взломанное приложение
  не перепишет себя; пишет оно только в `media/`, `private/`, `static/`, их создаёт автовыкладка.
  Прежний `deploy.sh` (через `git pull` на сервере), `Makefile` и `make deploy` убраны, код больше
  не заливается в папку проекта. Обновлению сервера: в `.env` — `DEPLOY_IMAGE=…:<хеш>` (dev-проект — `:dev`), администратор
  включает автовыкладку проекту; старые `app/`, `app.prev/`, `deploy.sh` в папке проекта можно удалить
  после первой выкладки.
- Образ бэкенда сам запускается не от root — пользователем 1000, как `user:` в `compose.yml`:
  без compose (`docker run`, панель вроде Dokploy) приложение тоже не root. Папки `media/`, `private/`,
  `static/` в образе — его: новый том Docker получает их с правом записи. Сайту ничего делать не нужно.
- Модуль `user`: каждый вход — сессия в базе, токены действуют, пока жива сессия. Выход гасит
  токены этого устройства сразу; новые `/logout/all`, `/session/list`, `DELETE /session/{id}`;
  смена и сброс пароля завершают все сессии; в админке у пользователя — его сессии.
  **Есть миграция** (`user`). Токены, выданные до обновления, недействительны — один раз войти заново.
- Одна точка входа — `project/asgi.py` под uvicorn, как локальный `runserver`. В light админка и API —
  одним процессом (`app`), в full — API (`app-full`), админка отдельным процессом (`admin`, число —
  `ADMIN_WORKERS`), Redis и воркер. `project/asgi_api.py`, `project/wsgi.py` и gunicorn убраны.
  Серверам на light делать ничего не нужно.
- Убраны эндпоинты, которые движок не вызывал: `/api/user/verify` и `/api/page/category/detail/{slug}`.
- Настройки модулей в `.env` — только капча: `FORM_CAPTCHA_PROVIDER` и ключи SmartCaptcha.
  `PAGE_IMAGE_*`, `FORM_TOKEN_LIFETIME_MINUTES`, `FORM_FILL_SECONDS_MIN`, `FORM_FILE_*`
  и `FORM_CAPTCHA_PASS_ON_ERROR` больше не читаются — их значения по умолчанию стали константами
  в `conf.py` модуля. Задавали что-то из них в `.env` сервера — теперь это значение в коде.
- Модуль `form`: в описании формы — `fill_seconds_min`, сколько ждать перед отправкой.
- Ядро: `core/routers.py` убран, модули — с обычным `APIRouter()`: формат ошибки 422 в Swagger
  задаёт сборка API для всех сразу.
- Модуль `user`: вход, активация, смена и сброс пароля отдают только `access`, refresh — в куке
  `httpOnly` для `/api/user/refresh`; `/refresh` берёт его из куки, тело не нужно; новый `/logout`
  стирает куку. Схемы `TokenPairOut`, `TokenRefreshIn`, `TokenRefreshOut` → одна `TokenOut`.
- Модуль `form`: в админке заявок — действие «Отправить письмо ещё раз» (письмо не дошло,
  заявку вернули из спама). Миграций нет.
- Ядро: мост `core/bridge.py` — асинхронный сервис вызывается из админки и команд
  (`@with_sync`, вызов `.sync(...)`): одно действие для API и админки пишется один раз.
- `/robots.txt` на домене бэкенда — запрет целиком: админке и Swagger в поиске не место.
- Профиль light: при перезапуске процесс дожидается начатых писем, а не обрывает их.
- Модуль `page`: админка больше не держит адреса страниц фронта (`login`, `lk`, `blog`…) — правило
  проще: адрес совпал со страницей фронта, показывается страница фронта. Заняты только адреса
  бэкенда: `admin`, `api`, `static`, `media`, `_nuxt`.
- Тесты: `python manage.py test --keepdb` (вход, страницы, заявки, мост); CI гоняет их перед каждой выкладкой.
- `compose.yml` — профили: `full` (как было) и `light` для контентных сайтов — админка и API
  одним процессом, задачи в нём же, без Redis и воркера: ~200 МБ вместо ~600. **На сервере
  обязательно** `COMPOSE_PROFILES` в `.env` — `full`, чтобы осталось как было, или `light`;
  без него поднимутся только `files` и `cron`. Переход на light — в `docs/deploy.md`.
