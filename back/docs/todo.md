## Не проверено

- **Профиль full на сервере.** С 30.09.2026 dev и прод работают в light. В нынешнем виде
  full — админка отдельным контейнером, очередь как поток Redis с подтверждением — ни на
  одном сервере не запускался, а тесты идут без Redis. Проверить с первым кабинетом: письмо
  проходит API → Redis → воркер; задача, поставленная до первого запуска воркера, выполняется;
  воркер, убитый посреди задачи, через 10 минут выполняет её повторно.
- **Вход на настоящих доменах.** Вход из браузера прямо в API с refresh в куке проверен
  локально (Chrome, `localhost:3000` → `localhost:8000`). На `site.ru` → `back.site.ru`,
  в том числе в Safari, — нет. Проверить с первым кабинетом.
- **Живые события через Redis.** Путь «событие → канал Redis → процессы API» проверен тестами
  с каналом в памяти и вручную с поддельным Redis (`fakeredis` по TCP): два процесса API, событие
  из `manage.py shell`, перезапуск Redis. С настоящим Redis — нет. Проверить на стенде в профиле full:
  две вкладки одного пользователя, событие из `manage.py shell` — `hub.send.sync(...)` — приходит
  в обе по разу; Redis перезапустили — вкладки на месте, следующее событие доходит.

## Не сделано

**Тесты.** Не покрыты: число запросов к базе
в списках. Postgres для тестов без Docker — pip-пакет `pgserver` (бинарники Postgres,
под Python 3.12).

**Под нагрузкой** — по итогам [замера](benchmark.md):

- **Списки на больших таблицах.** `paginate()` делает точный `count` и `offset`:
  на миллионе строк `count` стоит 60 мс процессора Postgres на каждый запрос,
  25 000-я страница — 214 мс. Нужны приблизительный или кэшированный `count`
  и постраничный вывод по `id` вместо `offset` для глубоких страниц.
- **Сколько стоит проверка ответа.** Догадка, не замер: `response_model` заново проверяет
  ответ по схеме и только потом превращает в JSON; ещё на каждую строку списка создаётся
  объект ORM. Когда будем дорабатывать `paginate()` — замерить, сколько процессора это
  съедает и что даёт выборка `.values()` без объектов. Разрыв с Node и Go это не закроет.
- **Скрипт нагрузочного теста** своего приложения: мимо Traefik (иначе в результате
  лимиты на один IP, а не бэкенд), генератор вне лимита процессора проекта, нагрузка
  с постоянной частотой — на замере это умел `vegeta`, `hey` шлёт залпами, `oha`
  не проверяли. За основу — `users.sh` из стенда замера (в открытый репозиторий не вошёл).
- **Лимит Traefik на запросы сервера сайта к API.** При рендере страниц сервер Nuxt ходит
  к API через Traefik, и для лимита на IP (около 150 одновременных на нашем сервере) все посетители —
  один адрес, контейнер сайта. Слой `page` снял это кэшем. Если упрётся другое (кабинет,
  каталог с рендером на сервере) — внутренний вход Traefik для контейнеров со своим, более
  высоким лимитом, открытый только внутренней сети сайта; снаружи лимиты прежние. Это правка
  настроек Traefik сервера, решает администратор. Объединять сайт и бэкенд в один проект — нет: пропадёт
  разделение доступа, и в 2 ГБ проекта они вместе не влезут.

**Разное:**

- Команда `sync_from_prod` — залить копию боевой базы в локальную, с бэкапом обеих.
- `TaskRun` со статусом задач в админке, мониторинг (Sentry, метрики). Если понадобится видеть
  задачи в админке — посмотреть Procrastinate: очередь в самом Postgres, без Redis.
- Уведомление об ошибках из журнала, например в Telegram. Поток, который пишет журнал,
  синхронный — фоновую задачу из него не поставить, и синхронного HTTP-клиента
  (`requests`, `httpx`) в зависимостях пока нет.
- Конструктор полей формы — когда понадобится.
- Живые события (модуль `live`): выход «везде» и смена пароля
  не закрывают уже открытое соединение — оно получает события, пока вкладка открыта.

## Идеи на потом

Обсуждены, отложены. Затрагивают и бэкенд, и фронт — делать парой, одним коммитом.

- **Шорткоды в тексте страниц**, синтаксис как в WordPress: `[form code="callback"]`,
  `[video url="…"]`, `[button text="…" href="…"]` — отдельной строкой. Бэкенд при сохранении
  находит их до Markdown (иначе типографика испортит кавычки), неизвестное имя — ошибка
  в админке; API отдаёт текст кусками: HTML, шорткод с параметрами, HTML. Фронт рисует
  шорткод компонентом `Shortcode<Имя>` — тем же, что разработчик ставит в странице:
  `<ShortcodeForm code="callback" />`. Каждый слой приносит свои шорткоды. Видео только
  с разрешённых площадок — так в статье появится плеер, а `iframe` по-прежнему вырезается.
  Для `[form]` нужен готовый компонент формы, рисующий поля по настройкам из админки.
- **Галерея фото.** Бэкенду — решить, где хранить фото и как отдавать их в API; картинки
  ужимать в webp, как в статьях. Фронту — компонент `PageGallery` в слое `page` на штатных
  компонентах Nuxt UI: карусель с лентой миниатюр и просмотр на весь экран. Готовой галереи
  в Nuxt UI нет, но переходить ради неё на PrimeVue 4 не стоит: он больше не развивается,
  а вторая система стилей поверх Tailwind утяжелит страницы. Увеличения фото в Nuxt UI тоже
  нет — если понадобится, небольшая библиотека просмотра только внутри галереи. В статью
  галерея встанет шорткодом `[gallery code="…"]`.

## Решили не делать

- **Менять ORM.** Tortoise оставлен осознанно: миграции делает Django (слабое место
  Tortoise не используется), синтаксис как у Django ORM, на замере вдвое быстрее
  Django. Запросы держать в сервисах — тогда замена, если понадобится, затронет один слой.
- **Меню сайта в админке.** Меню живёт в компоненте шапки сайта: оно сплетено с дизайном
  (иконки, выпадающие блоки, кнопка-призыв), правка в коде — минута и видна в git. Рубрики
  блога и так приходят из админки. Вернуться, только если клиенту понадобится менять меню
  самому, без разработчика.
