# Ядро проекта
Общее для всех модулей · 25.10.2026

`core` — не модуль с фичей, а общий слой: то, чем пользуются все остальные модули.
Своих таблиц, админки и эндпоинтов у него нет, в Swagger и в админке он не виден. Модель одна, абстрактная, —
основа таблиц истории изменений, которые модули заводят у себя.

Правило простое: переиспользуемое между модулями — в `core`, настройка конкретного
проекта (какие приложения, какие ключи, как запускается) — в `project`.

## Что здесь лежит

| Что | Зачем |
|---|---|
| Общие схемы ответов | типовые ответы и формат ошибки 422 в Swagger |
| Пагинация, сортировка и фильтры | один формат списков на весь API; фильтр — схема, поле → лукап Tortoise |
| Обработка ошибок | любая ошибка выходит наружу в одном формате, на русском |
| Переводы ошибок валидации | сообщения Pydantic по-русски |
| Подключение к базе для API | асинхронный доступ к тем же таблицам, что у Django |
| Генератор моделей | `models_async.py` из Django-моделей |
| Фоновые задачи | брокер и правила запуска задач |
| Кэш | `cache.py`: справочник из кэша одной строкой в сервисе, сброс при правке в админке; без Redis кэша нет |
| Мост для админки | асинхронный сервис API вызывается из админки и команд |
| Письма | отправка по шаблону |
| Клиент внешних API | `http.py`: одна сессия на процесс, таймаут 60 с; сервис не ответил — `502` с понятным текстом |
| История изменений | `history.py`, `history_admin.py`: кто, когда и что поменял в записи — было → стало |
| Слаг из текста | `slug.py`: транслит кириллицы — одинаковые адреса у всех модулей |
| Дерево | `tree.py`: плоский список с `parent_id` → вложенный JSON, узел с потомками для фильтра, перенос без цикла |
| Настройки модулей | `env.py`: настройка из `.env` со значением по умолчанию и проверкой границ — в `conf.py` модуля; что действует — `manage.py env_settings` |
| Файл от посетителя | `upload.py`: проверка формата и размера, случайное имя на диске, уборка неприложенных, выдача закрытого файла из API |
| Картинки | `image.py`: картинка → webp, ширина до предела, поворот по EXIF — из админки любого модуля |
| Браузер посетителя | User-Agent для людей — «Chrome, Android, телефон»: в заявках и в списке сессий |

| Свой `runserver` | админка и API на одном порту локально |
| Основа тестов API | клиент FastAPI на настоящей базе, ожидание задач |

## Списки

Списки с пагинацией в API выглядят одинаково: `{"items": [...], "total": {"count": N}}`.
Фронт разбирает их одним и тем же кодом, и не приходится каждый раз договариваться
о названиях полей. Короткие списки без пагинации — справочники (`/info`), сессии
пользователя — отдаются просто массивом.

```python
from core.pagination import ListOut, Pagination, paginate, sort_queryset

@router.get("/list", response_model=ListOut[ProductOut], summary="Список товаров")
async def product_list(pagination: Pagination, sort: str = "-id"):
    queryset = sort_queryset(Product.all(), sort, ["id", "title", "price"])
    return await paginate(queryset, pagination)
```

Страница задаётся параметрами `page` и `row`, по умолчанию 20 записей, больше 1000
за раз отдать нельзя. Номер страницы — до 10 000: дальше `422`, а не ошибка базы на огромном
смещении. Каждая запись получает `row_number` — сквозной номер по всей
выборке, а не по странице: на второй странице нумерация продолжается, а не начинается
заново. Поле должно быть объявлено в схеме ответа, иначе его не будет видно.

Сортировка приходит параметром `sort`, префикс `-` — по убыванию. Сортировать можно
только по полям, которые эндпоинт разрешил явно: по остальным приходит `406` с перечислением
допустимых. Это не придирка — сортировка уходит прямо в базу, и произвольное поле в ней
означает произвольный запрос к любой связанной таблице.

При равных значениях записи идут по `id`, новые первыми. Без второго ключа база отдаёт
равные записи в любом порядке, и он может меняться от запроса к запросу: статьи с одной датой
на границе страниц ленты то повторялись бы на соседней странице, то не попадали ни на одну.

Каждый список — два запроса к базе: сначала общее количество, потом сама страница.
Про `count` стоит помнить на больших таблицах: он считает все строки, подходящие под фильтры.

Фильтры — схема из `core.filters`: каждое поле — параметр запроса и лукап Tortoise, через который он
попадает в запрос. Свой разбор параметров в эндпоинте не писать.

```python
from core.filters import FilterField, FilterSchema

class ProductFilter(FilterSchema):
    status: str | None = FilterField("status", description="Статус")
    search: str | None = FilterField(["title__icontains", "sku__icontains"], description="По названию и артикулу", max_length=200)
    price_from: int | None = FilterField("price__gte", description="Цена от")
    category_id: list[int] | None = FilterField("category_id__in", description="Рубрики: ?category_id=1&category_id=2")

@router.get("/list", response_model=ListOut[ProductOut], summary="Список товаров")
async def product_list(pagination: Pagination, filters: Annotated[ProductFilter, Depends(ProductFilter.query)], sort: str = "-id"):
    queryset = sort_queryset(filters.apply(Product.all()), sort, ["id", "title", "price"])
    return await paginate(queryset, pagination)
```

Образец в шаблоне — лента блога: `PageListFilter` в `page/schemas.py`, эндпоинт `page_list` в `page/rest.py`.

Лукап — любой, который понимает Tortoise: без суффикса — точное совпадение, `__icontains`, `__gte`/`__lte`,
`__in` со списком, через связь — `category__slug`. Список лукапов — запись подходит, если подошёл любой (поиск
по нескольким полям); разные поля — все сразу. Не заданное поле и пустая строка запрос не меняют: пустое поле
формы на сайте не прячет записи.

В Swagger каждое поле — отдельным параметром со своим описанием и ограничениями. Неверное значение (дата `abc`)
— `422` у поля, ошибка своего валидатора схемы — `422` с его текстом. Параметр, которого эндпоинт не объявил, — тоже `422`, а не тихий
пропуск: опечатка `?staus=new` иначе отдала бы весь список, и это заметили бы не сразу. `page`, `row`, `sort`
и другие параметры эндпоинта — не лишние. Правило «`date_to` без времени — до конца дня» (`back/CLAUDE.md`)
фильтр сам не делает: такому полю нужен свой валидатор.

## Ошибки

Наружу всё выходит в одном виде — объект с полем `message` на русском. Разбирать
формат по коду ответа фронту не нужно.

- Бизнес-ошибка — `406` и текст, который можно показать пользователю.
- Ошибка валидации — `422`: в `message` все проблемы одной строкой, в `full_error` —
  разбор по полям. Переводы подставляются по коду ошибки Pydantic, а не по английскому
  тексту: коды между версиями стабильны, тексты меняются. Незнакомый код оставит
  английское сообщение — значит, его стоит добавить в переводы.
- Ошибка поля, которую нашёл сервис, а не схема (обязательное по настройкам, «телефон или
  email»), — тоже `422` в том же виде: `raise field_error({"phone": "Текст"})`. Сайт покажет
  её под полем, а не общим сообщением. `406` — для того, что к полю не относится.
- Запрошенная запись не найдена — `404` «Не найдено». Имя модели наружу не уходит:
  по тексту ошибки нельзя изучать устройство базы.
- Внешний сервис не ответил или ответил ошибкой — `502` «Сервис «…» недоступен», см. [Внешние API](#внешние-api).
- Всё остальное — `500` «Внутренняя ошибка сервера». Подробности не показываем,
  но трейсбек попадает и в stdout, и в журнал, см. [модуль «Журнал»](../log/readme.md).

## База для API

Подключение Tortoise собирается из настроек Django: база одна, описана в одном месте,
разъехаться настройкам негде. Время везде UTC — и Django, и API пишут в базу одинаково.

У каждого процесса API свой пул соединений (`API_DB_POOL_SIZE`). Ограничение, о котором
легко забыть при масштабировании: **число процессов × размер пула** не должно превышать
`max_connections` PostgreSQL, иначе новые процессы начнут получать отказ от базы.

Генерация `models_async.py` описана в [architecture.md](../../docs/architecture.md).
Здесь достаточно одного: генератор не угадывает.
Незнакомое поле — ошибка команды, а не молчаливая подмена на что-то похожее. Модели
сторонних приложений не генерируются, они остаются только на стороне Django.

## Фоновые задачи

Задача объявляется в `<module>/tasks.py` и вызывается из сервиса. Вызов не ждёт
результата: основное действие завершается, задача уходит в очередь.

Объявлять задачу — только в `tasks.py`: воркер знает задачи из этих файлов. Объявленную
в другом месте локально, без Redis, выполнит сам процесс API, а воркер на сервере может её
не найти — и поломка видна только там.

```python
@broker.task                       # tasks.py модуля, broker — из core.broker
async def send_report(user_id: int) -> None: ...

await send_report.kiq(user.id)     # в сервисе
```

Работает это двумя способами, в зависимости от того, задан ли `REDIS_URL`:

- **Задан** — задачи складываются в Redis, их разбирает отдельный процесс-воркер.
  Так на сервере: если API перезапустят, очередь не пропадёт. Задача уходит из очереди,
  только когда выполнена: если воркер упал посреди неё, через 10 минут её заберёт другой.
  Поэтому задача может выполниться дважды и должна это спокойно переживать — повторное
  письмо с кодом не беда, повторное списание денег недопустимо.
- **Не задан** — задача выполняется тут же, в процессе API. Локально это удобно,
  Redis и воркер не нужны. Но задача при этом живёт в том же процессе: при остановке он
  дожидается начатых задач, а если его убили или задача висит дольше, чем ждёт docker, —
  потеряли.

Туда уносится то, чей результат не нужен пользователю сразу (письма, отправка данных
во внешние системы), и то, что грузит процессор или базу (отчёты, выгрузки). Процесс API
обслуживает много запросов сразу, и тяжёлый расчёт в нём останавливает не один запрос,
а все. А вот ждать внешний сервис, ответ которого нужен пользователю сейчас, можно прямо
в запросе через [клиент внешних API](#внешние-api): асинхронное ожидание процесс не занимает — ради этого API
и асинхронный (см. [замер](../../docs/benchmark.md)).

## Кэш

Справочник, который сайт читает часто, а меняют редко и в админке, — из кэша. В модуле две строки:

```python
from core import cache

# services.py: из кэша, а нет — из базы и в кэш на 10 минут
return await cache.get_or_set("page:category_list", lambda: models_async.PageCategory.filter(is_active=True).values("id", "name", "slug"), ttl=600)

# apps.py, в ready(): рубрику сохранили или удалили в админке — ключ сброшен
cache.clear_on_change(PageCategory, "page:category_list")
```

- **Где лежит.** С `REDIS_URL` (профиль full) — в Redis, общем для всех процессов API и админки. Без него кэша нет:
  каждый раз из базы. Кэш в памяти процесса не подходит: процессов API бывает несколько, админка — свой процесс,
  и после правки в админке остальные отдавали бы старое.
- **Что хранить** — словари, списки, строки: то, что уйдёт в ответ. Не объекты ORM: `.values(...)`, схема ответа
  соберётся из словаря.
- **Срок обязателен**, без него — ошибка. Redis при нехватке памяти вытесняет только ключи со сроком: ключ без срока
  остался бы навсегда, а при полной памяти Redis отказал бы в записи всем, и очереди задач тоже. Срок — минуты:
  правка мимо админки видна не позже.
- **Сброс — только при сохранении через Django:** `save()` и `delete()` — это админка, правка прямо в списке,
  «удалить выбранные» и команды. Сигнал здесь не ведёт логику, а сбрасывает кэш: справочник правят в админке,
  API его только читает. Запись из API через Tortoise и `QuerySet.update()` сигналов не шлют — кэш доживёт
  до конца срока.
- **Ответ — один для всех.** Справочник, у которого каждому пользователю или компании свой ответ, — без кэша:
  сброс знает только ключи, названные в `ready()`, и ключ вида `…:user:42` после правки в админке не сбросится —
  пользователь увидит старое до конца срока.
- **Кэш некритичный.** Redis не ответил — справочник из базы, в журнале предупреждение; не сбросился ключ — сохранение
  в админке проходит, старое значение живёт до конца срока.
- **Кэш целиком не очищать** (`clear()` у кэша Django): в Redis это стирает всю базу, а в ней и очередь задач.
  Сбросить ключ — сохранить запись.
- **В тестах кэша нет**, как без Redis. Проверить, что кэш работает и сбрасывается, — `override_settings` с `LocMemCache`,
  образец — `page/tests/test_category_cache.py`.

## Асинхронный сервис из админки

Сервисы API асинхронные и ходят в базу через Tortoise, а админка и команды `manage.py`
синхронные: асинхронную функцию напрямую они вызвать не могут. Чтобы действие, нужное
и в API, и в админке, не писать дважды на двух ORM, у сервиса есть синхронный вызов
`.sync(...)`. Код сервиса один.

### Как вызвать

Сервис в `services.py` модуля помечается декоратором — больше в нём ничего не меняется:

```python
from core.bridge import with_sync

@with_sync
async def cancel_order(order_id: int, reason: str) -> None:
    ...  # Tortoise, задачи, HTTPException(406, "...") — как в любом сервисе API
```

API и задачи вызывают его как обычно: `await services.cancel_order(order.id, "...")`.

**Из админки — действием над выбранными записями.** Основной способ: менеджер отмечает
записи и выбирает действие в списке.

```python
from django.contrib import admin, messages
from fastapi import HTTPException

class OrderAdmin(admin.ModelAdmin):
    readonly_fields = ["status"]   # статус — только действием: у смены есть последствия
    actions = ["cancel"]

    @admin.action(description="Отменить заказ")
    def cancel(self, request, queryset):
        for order_id in queryset.values_list("id", flat=True):
            try:
                services.cancel_order.sync(order_id, f"Отменён менеджером {request.user}")
            except HTTPException as exc:   # бизнес-ошибка сервиса — сообщением в админке
                self.message_user(request, f"Заказ №{order_id}: {exc.detail}", messages.ERROR)
```

Рабочий пример — действие «Отправить письмо ещё раз» в админке заявок (`form/admin.py`).

**Из админки при сохранении формы** — только если без обычного поля в форме не обойтись.
Вызов — после коммита: до него Tortoise не видит того, что админка сохранила.

```python
from django.db import transaction

def save_model(self, request, obj, form, change):
    super().save_model(request, obj, form, change)
    if "status" in form.changed_data:
        transaction.on_commit(lambda: services.after_status_change.sync(obj.id))
```

Отказать здесь сервис уже не сможет — запись сохранена. Проверку «можно ли» тогда
делают в `clean()` формы.

**Из команды `manage.py`** — так же, `.sync(...)`:

```python
class Command(BaseCommand):
    def add_arguments(self, parser):
        parser.add_argument("order_id", type=int)

    def handle(self, *args, **options):
        services.cancel_order.sync(options["order_id"], "Отменён командой")
```

В `manage.py shell` — тоже: `services.cancel_order.sync(5, "проверка")`.

### Когда это нужно, а когда нет

- **Проверки и расчёты без базы** — обычная функция, её зовут обе стороны без всякого
  моста (пример — проверка полей заявки в модуле «Заявки»).
- **Простая правка данных** — тексты, названия, настройки — админка делает сама, через Django.
- **Действие с последствиями** — письмо, смена остатков, запись в историю — и **постановка
  фоновой задачи** из админки: асинхронный сервис через `.sync(...)`. Поле с такими
  последствиями в админке только для чтения, меняется оно действием.

В `save()` и сигналы последствия не кладём: из API они не вызываются, а из админки
сработали бы и при правке скриптом.

### Как работает и что помнить

Админка живёт в одном процессе с API — и локально, и на сервере, — и вызов идёт через
уже открытые соединения API. В командах `manage.py` своего API в процессе нет —
мост на время вызова сам открывает соединение с базой и закрывает его после. Для нажатия
кнопки это незаметно, а для тысяч вызовов подряд не годится: массовое — в фоновую задачу.

- Передавать номер записи, а не объект из админки: сервис работает со своей ORM.
- Общей транзакции с Django нет: если рядом сохраняли через Django — вызывать после коммита.
- Без Redis задачи, которые поставил сервис, выполняет тот же процесс. Из админки их доделывает
  процесс API, и кнопка отвечает сразу. В команде `manage.py` мост их дожидается — иначе они
  оборвались бы вместе с вызовом, — поэтому команда завершается после отправки письма.
- Из асинхронного кода (API, задачи) — только `await`: `.sync()` там выдаст ошибку.

## Слаги

Слаг из текста — `slugify_text(title)` из `core.slug`: свой транслит кириллицы, латиница, цифры и дефис.
Штатный `prepopulated_fields` админки транслитерирует иначе (ё → yo, щ → sh) — адреса модулей разошлись бы.
Уникальность слага проверяет сам модуль: `slugify_text` только делает строку, занят ли адрес — решает модуль.

## Дерево

Рубрики каталога, вложенные страницы, папки хранятся плоско: у записи — ссылка на родителя (`parent`). Сайту нужно
дерево целиком (меню рубрик), фильтру товаров — рубрика со всеми подрубриками, админке — перенос рубрики без цикла.
Всё это — `core.tree` поверх строк из базы: дерево собирается в памяти из одного запроса. Рубрик и страниц сотни
или тысячи, не миллионы: тысяча узлов собирается примерно за миллисекунду, 10 000 — за 10 мс. Поэтому сборка
идёт прямо в запросе API, а особое хранение дерева в базе не нужно.

```python
from core.tree import build_tree, check_parent, descendant_ids

rows = await Category.all().values("id", "parent_id", "title", "slug", "sort_order")
tree = build_tree(rows, order=("sort_order", "id"))
```

Образец — рубрики блога: справочник деревом — `category_list` в `page/services.py`, перенос без цикла — форма
рубрики в `page/admin.py`.

- **Дерево в ответе API** — `build_tree`: корни, у каждого узла дети — в `child_list`, на каждом уровне — по полям
  `order`. Схема ответа рекурсивная — `child_list: list["CategoryTreeOut"]`: поля строки, которых нет в схеме
  (`parent_id`, `sort_order`), в ответ не попадут.
- **Рубрика с подрубриками** — `descendant_ids(rows, category_id)`: id самой рубрики и всех вложенных на любую глубину,
  для фильтра `Product.filter(category_id__in=…)`.
- **Перенос узла** — `check_parent(rows, node_id=…, parent_id=…)` до записи: под себя или под своего потомка —
  `ValueError`, иначе ветка замкнулась бы в цикл и пропала из дерева. В сервисе API — `field_error({"parent_id": …})`,
  сайт покажет ошибку под полем; в админке — `ValidationError` в `clean()` формы. Перенос в корень и новый узел
  (`node_id` — `None`) проверку проходят всегда.

Что стоит знать:

- Узел — словарь, строка `.values()` Tortoise или Django, а не объект ORM: в дерево попадают только запрошенные
  поля. В строке нужны `id`, `parent_id` и поля `order` — забытое поле даёт `KeyError`, а не молча плоский список.
- Родителя нет в списке — узел становится корнем, а не пропадает. Поэтому фильтр в запросе (только опубликованные)
  поднимет в корень детей скрытой рубрики; спрятать ветку целиком — убрать из строк и её потомков (`descendant_ids`).
- Цикл, уже записанный в базу (1 → 2 → 1), обход не зацикливает, но его узлы и их потомки в дерево не выходят —
  ни корнем, ни ребёнком. Узел, который сам себе родитель, — корень. Поэтому перенос — только через `check_parent`.
- В полях `order` не должно быть пустых значений: Python не сравнивает `None` с числом, и сборка упадёт.
- В ответе API — не глубже 254 уровней: дальше pydantic принимает вложенность за цикл (`recursion_loop`), и ответ — 500.
  `check_parent` глубину не ограничивает; рубрикам и папкам столько уровней не нужно.

## Файл от посетителя

Файл к заявке или анкете грузится в два шага: сайт отправляет файл отдельно и получает `file_id`, потом передаёт
его вместе с записью. Так ошибка файла приходит до отправки записи, а запись уходит обычным JSON, без файлов.

Общее — в `core.upload`: эндпоинт читает файл `read_upload` (не больше предела), сервис проверяет `check_upload`
и сохраняет `save_upload`, команда уборки — `clear_orphans`. Проверка — формат по расширению без учёта регистра,
пустой файл, размер: `406` с текстом для посетителя, в этом порядке. Содержимое не проверяется — под `.pdf` может
прийти что угодно. Имя на диске случайное (`ГГГГ/ММ/<uuid>.pdf`): имя посетителя в путь не попадает и чужой файл
не затирает, исходное модуль хранит в записи.

Остальное — в модуле: модель с `FileField` в закрытой папке вне `media/` (`media/` открыта всем по прямой ссылке,
а в файлах бывают сканы документов), привязка к записи, право на скачивание и строка уборки в `project/crontab`.
Образец — файлы заявок: `form/services.py`, раздел «Файлы» в [readme модуля](../form/readme.md#файлы).

Скачать закрытый файл из API — эндпоинт модуля: право решает модуль, `core` только отдаёт файл.
Сервис находит запись файла с проверкой права одним запросом и возвращает `file_response`:

```python
my_file = await models_async.MyFile.get(id=file_id, record__user_id=user.id)  # чужой — 404, как несуществующий
return await upload.file_response(models.file_storage(), my_file.file, my_file.original_name)
```

Путь к файлу — только из записи в базе, не из запроса: в адресе — `id` записи, за папку хранилища имя из записи
не выйдет. Нет права — тот же `404`, что на несуществующий файл: по ответу не узнать, что файл есть. Файла нет
на диске — тоже `404`, а не `500`. Ответ — скачивание (`attachment`, имя посетителя с кириллицей по RFC 5987),
тип — по расширению на диске, `nosniff`, `Cache-Control: private, no-store`: файл не откроется в браузере
как страница и не осядет в кэше прокси. Читается потоком, а не целиком в память.

## Картинки

Картинка, которую загружают в админке (обложка, картинка в тексте, товар, аватар), — `to_webp` из `core.image`:

```python
content, extension = to_webp(upload.read(), extension, width_max=conf.IMAGE_WIDTH_MAX)
```

Шире `width_max` — ужимается с той же пропорцией и переводится в webp: фото с телефона на 8 МБ
иначе замедлит страницу. Поворот, который телефон записал в снимок тегом EXIF, применяется сразу — в webp тег
не переходит, и вертикальное фото легло бы на бок. Прозрачность png остаётся. gif — как есть: может быть анимированным.
Как есть, даже не ужатой, остаётся и очень длинная картинка — выше 16 383 точек после ужатия (предел webp):
png 1080×16 383 станет webp, 1080×16 384 и 3200×40 000 останутся тем же png.

Чего не делает. Формат и размер файла не проверяет — это правила модуля (`check_image` у страниц) или `core.upload`.
Не картинку и битый файл не отвергает: файл, который не открылся или не дочитался, возвращается как есть,
с прежним расширением, — оптимизация не мешает загрузке. Поэтому что это картинка, модуль проверяет до вызова:
`forms.ImageField().to_python(upload)` отсекает не картинку — текст под `.jpg`, svg под `.png`, пустой файл.
Обрезанный jpeg (заголовок целый, данные оборваны) эта проверка пропускает, `to_webp` его не читает, и он ляжет
на диск как есть — битым `.jpg`. Предел ширины — настройка модуля (`PAGE_IMAGE_WIDTH_MAX`
у страниц): своих настроек картинок у `core` нет. Файл не сохраняет — возвращает байты и расширение.

Образец — `prepare_image` в `page/services.py`: расширение и размер, картинка ли это, `to_webp`, случайное имя файла.

## История изменений

Кто, когда и что поменял в записи — было → стало. Первые — статусы заявок: блок «История» внизу заявки.

Таблица истории своя у каждой модели и лежит в её модуле: одна общая на проект разрасталась бы и связывала
модули между собой. Модуль заводит её на основе `HistoryModel` из `core.history`:

```python
class FormRequestHistory(HistoryModel):
    record = models.ForeignKey(FormRequest, models.CASCADE, related_name="history", verbose_name="Заявка")
```

Пишут в неё двое:
- админка — `HistoryAdmin` из `core.history_admin` вместо `admin.ModelAdmin` и поля в `history_fields`: правки
  в карточке и прямо в списке; на странице записи — блок «История», только для чтения;
- сервис API — декоратор `@history(models_async.FormRequestHistory, ["status"])`: читает строку до вызова и после
  и пишет разницу в той же транзакции; кто — аргумент `user` сервиса: пользователь или его id, без него — система.

Пишется только то, что перечислено: история — не копия записи. Поле с персональными данными (телефон, email) —
ещё и в `history_hidden` админки или `hidden` декоратора: в истории останется только факт «изменено».

Не сигналы и не готовые библиотеки: API пишет через Tortoise мимо сигналов Django, а `filter().update()` обходит
сигналы обеих ORM — `django-simple-history` и `auditlog` таких правок не видят. Декоратору всё равно, как сервис
поменял строку: он сравнивает базу до и после.

Удалили запись в админке — история уходит с ней. Из API запись с историей удаляется после истории:
`await FormRequestHistory.filter(record_id=...).delete()`.

Сервис под `@history` выполняется целиком в одной транзакции. Задачу в очередь (`.kiq`) ставить после вызова
сервиса, а не внутри: иначе воркер может взять её и прочитать строку раньше, чем транзакция закоммитится.

Поле из `history_fields` удалили или переименовали — старые строки истории показываются под прежним именем поля,
значения — как записаны, без подписей из `choices`. Страница записи из-за них не падает.

Убрать модуль с историей — как любой модуль, `migrate <модуль> zero`: таблица истории — его, уходит вместе с ним,
в `core` ничего не остаётся.

## Внешние API

Запрос к внешнему сервису из модуля — одна строка:

```python
from core import http

data = await http.request_json("GET", url, service="Поиск запчастей", params={"q": number})
```

- **Сессия одна на процесс** (`aiohttp`): соединения с сервисом переиспользуются, а не открываются на каждый
  запрос. Закрывается при остановке API и воркера, у вызова сервиса из команды `manage.py` — в конце вызова.
  Почему `aiohttp`, а не `httpx`, — [architecture.md](../../docs/architecture.md#что-легко-сломать).
- **Таймаут — 60 секунд**: без него запрос к зависшему сервису висит вечно. Свой — в вызове,
  `timeout=aiohttp.ClientTimeout(total=10)`.
- **Сбой сервиса** — нет связи, таймаут, ответ 400 и выше, не JSON — `ExternalServiceError`. Не поймали —
  API отвечает `502` «Сервис «Поиск запчастей» недоступен. Попробуйте позже», в журнал — предупреждение
  одной строкой: что ответил сервис. Поэтому `service` — название для человека. Свой ответ на сбой —
  `except http.ExternalServiceError as error`: в `error.status` код ответа сервиса, `None` — ответа не было.
- **Свой разбор ответа** (статусы, текст, заголовки) — `http.session()` напрямую:
  `async with http.session().post(url, data=data) as response`. Так проверяет капчу модуль `form`:
  при сбое Яндекса заявка проходит, а не получает `502`.

## Письма

Письмо собирается по шаблону из `templates/email/` модуля, который его отправляет. Папка
`email/` у всех модулей общая, поэтому имя шаблона — уникальное на проект. Текстовая версия
делается из того же HTML — писать два варианта руками не нужно. Название и адрес сайта
подставляются в шаблон сами, из настроек.

Отправлять только из задач. В эндпоинте почтовый сервер задержит ответ на всё время
соединения, а если он недоступен, вместе с письмом упадёт и основное действие —
регистрация или смена пароля.

Тексты писем — на русском, ссылки берут домен из `SITE_URL`, а не из запроса:
письмо не должно зависеть от того, с какого адреса пришёл пользователь.

## Выгрузка в Excel

Список админки выгружается в xlsx действием «Выгрузить в Excel»: модуль ставит `export_xlsx` из `core.xlsx`
в `actions` своей админки. Колонки и их порядок — как в списке (`list_display`), строки — отмеченные или все
под фильтром («Выбрать все»), в порядке списка. Статус — подписью («Новая»), а не кодом; дата — датой Excel
по времени сайта. Выгружает тот, кто видит список, — право «просмотр» на модель.

Текст попадает в таблицу только текстом. Имя `=HYPERLINK(…)` из формы сайта иначе стало бы формулой в Excel
менеджера, а `#N/A` — ошибкой. Телефон `+7…` не трогается: в xlsx у ячейки свой тип, и строку Excel числом
или формулой не читает. Управляющие символы из текста посетителя убираются — Excel их не принимает,
и одна такая заявка сломала бы всю выгрузку.

Таблица собирается прямо в запросе админки: 10 000 строк — несколько секунд. Списки на сотни тысяч
строк — выгружать фоновой задачей.

## Настройки модулей

Каждая настройка модуля — в `.env` проекта с префиксом модуля (`FORM_`, `PAGE_`, `USER_`, `LOG_`); нет строки —
значение по умолчанию из `conf.py` модуля. Так, потому что сайты работают на общем образе бэкенда и код
поменять не могут: своё значение им задать можно только в `.env`. Список настроек — в readme модуля,
все с умолчаниями — в `.env.txt`.

Модуль читает настройку одной строкой — `env_int`, `env_list` или `env_str` из `core.env`:

```python
IMAGE_WIDTH_MAX = env_int("PAGE_IMAGE_WIDTH_MAX", 1600, min_value=100)
```

- **Неверное значение** — не число, вне границ, не из списка, пустой список — останавливает запуск с ошибкой, где названы
  настройка и значение. Лучше не подняться, чем молча работать не так: выкладка остановится до миграций,
  прежняя версия продолжит работать. Поэтому `conf.py` модуля читается при запуске Django — из `apps.py`
  или `models.py`, а не с первым запросом.
- **Поменяли `.env`** — пересоздать контейнеры (`docker compose up -d --force-recreate`): `restart`
  новый `.env` не читает. Что действует на самом деле — `manage.py env_settings` в работающем контейнере
  (`docker compose exec app …`): все настройки модулей по разделам, значение и откуда оно (`.env`
  или по умолчанию); ключи — только «задан» или «пусто».
- **Новая настройка** — строкой в `.env.txt`, в раздел своего модуля, закомментированной, со значением
  по умолчанию: тест `core/tests/test_env.py` не пропустит настройку, которой нет в шаблоне.
- **Тесты** рассчитаны на значения по умолчанию: тест, которому важно число, подставляет его сам
  (`mock.patch.object(conf, ...)`), чтобы не зависеть от `.env` того, кто запускает.
- **В коде** остаются только пути, связанные с томами в `compose.yml`: другой путь из `.env` увёл бы
  файлы мимо тома.

## Локальный запуск

`manage.py runserver` здесь свой и перекрывает стандартный: стандартный про FastAPI
не знает и поднял бы только админку. Поэтому локально админка и API живут на одном
порту, и Swagger доступен сразу — `/api/docs`.

Команда только для разработки. На сервере — тот же `project/asgi.py` под uvicorn: в профиле light
админка и API одним процессом, в full админка — отдельным, см. [deploy.md](../../docs/deploy.md).

## Что класть в core, а что нет

Сюда — то, что нужно нескольким модулям и не зависит от предметной области проекта:
формат ответа, обработка ошибки, отправка письма, постановка задачи.

Не сюда — логика конкретной области, даже если её «наверное, переиспользуют».
Пока пользователь один, она живёт в своём модуле. Общий слой, в котором лежат чужие
правила, перестаёт быть общим: его нельзя взять в следующий проект целиком.

`core` не импортирует модули проекта (`user`, `form`, …): иначе модуль нельзя убрать, не сломав
основу. Следит тест `core/tests/test_independence.py`.

## Шпаргалка

- Список — через пагинацию и сортировку из `core/pagination.py`, в схеме нужно `row_number`.
- Сортировка — только по разрешённым полям, остальное `406`.
- Дерево из плоского списка — `core.tree`: `build_tree`, `descendant_ids`, перенос — `check_parent`.
- Бизнес-ошибка — `406` с текстом для пользователя; `404` и `500` подробностей не выдают.
- Новый код ошибки валидации по-английски — добавить перевод в `core/translations.py`.
- В `tasks.py` — письма, отправка во внешние системы, тяжёлые расчёты и отчёты; внешний вызов, ответ которого нужен сразу, — в запросе через `core.http`.
- Процессы API × размер пула ≤ `max_connections` базы.
- Действие и в API, и в админке — один асинхронный сервис с `with_sync`, в админке — `.sync(...)` из кнопки, не из `save()`.
- История изменений — таблица `<Модель>History(HistoryModel)` в модуле, в админке `HistoryAdmin` и `history_fields`, в сервисе `@history`.
- Справочник из кэша — `cache.get_or_set` в сервисе со сроком, `cache.clear_on_change` в `ready()` модуля.
- Файл от посетителя — `core.upload`: проверка, случайное имя, уборка, выдача из API (`file_response`); модель файла в закрытой папке и право на скачивание — в модуле.
