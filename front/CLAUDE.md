# CLAUDE.md

Движок сайтов на **Nuxt 4** из слоёв (`layers/*`) — фронт `web-start`, пара к бэкенду
в `../back` (Django + FastAPI). Сайты — отдельные репозитории, подключают движок
по тегу версии. Устройство, запуск, версии — [readme.md](readme.md). Перед работой над слоем —
его `readme.md`: там правила, которых по коду не видно.

## Команды
Выполняй сам: `npm run test`, `npm run typecheck`, `npm run build`, `npm run api:types`
(типы из кода `../back` через его `.venv`, базу не трогает).
Не выполняй, только покажи: деплой, docker.

## Слои
- Слой — `layers/<имя>/`: `nuxt.config.ts` (можно пустой), `app/` (pages, components,
  composables, utils, middleware, plugins), `server/`, `tests/`, `readme.md`.
- Имя слоя = имя модуля бэкенда, с которым он работает.
- Зависимости: только от `core` (и `user`). Слои друг друга не импортируют.
  Типы API — `import type { components } from '#api-types'`. Не `#layers/…` и не `~/…`:
  когда сайт подключает движок из git, этих путей нет.
- Пути к файлам в `nuxt.config.ts` слоя — от `import.meta.url`: относительный путь считался бы
  от папки сайта.
- Слой даёт логику и компоненты по умолчанию; сайт перекрывает их файлом с тем же именем в `app/`.
- Страницы слоя — только логика (данные, SEO, коды ответа), вид — в компонентах: сайт перекрывает
  компонент и продолжает получать исправления страницы.

## Движок и демо-сайт
- Корень репозитория — движок сайтов: `nuxt.config.ts` подключает слои `core`, `form`, `page`,
  в `app/` — общее по умолчанию. Слой `user` — для личного кабинета, в движок сайтов не входит.
- `.playground/` — демо-сайт: на нём движок разрабатывают и проверяют, его `.env` — там же.
  Всё сайтовое (шапка, главная, экраны кабинета) — только туда, не в корень.
- Изменил «договор» движка с сайтом — то, что описано в readme слоя и в таблице «Что сайт может поменять»
  `readme.md` (composables, имена и свойства компонентов, адреса страниц, настройки `app.config`, переменные
  окружения), — запись в `../CHANGELOG.md`
  (корень репозитория): что сломается и что сделать сайту. Не описанное в readme (`utils`) —
  внутреннее, меняется свободно. Новое, что сайт может поменять (компонент, ключ `app.config`, переменная), —
  ещё и строка в эту таблицу.
- Чистые функции — в `app/utils` слоя и с тестами в `tests/`. Composables — тонкая обёртка над ними.
- Массивы в `app.config` слоёв сайт не заменяет, а дописывает (слои сливаются через `defu`):
  в массиве движка — только то, что нужно всем сайтам, убрать лишнее сайт не сможет.

## UI — Nuxt UI 4
- Экраны — на компонентах Nuxt UI: формы, таблицы, кабинет (`UDashboard*`), страницы сайта
  (`UPage*`). Свой компонент — только если в Nuxt UI такого нет.
- Стили — классами Tailwind 4 в разметке, без `<style>` и своих CSS-файлов. Цвета — семантическими
  классами (`text-primary`, `text-muted`), не `text-blue-500`: палитра задаётся в `app/app.config.ts`,
  смена бренда — одна строка.
- Ошибки бэкенда: `fieldMap` — под полями, `message` — в `UAlert`. Форма кабинета (`UForm`, `UAuthForm`) —
  через `setErrors`, образец — `.playground/app/pages/login.vue`. Форма заявки (`useSiteForm`) — `:error`
  у `UFormField`, ошибки уже в её `error`; образец — `.playground/app/pages/index.vue`.
- Иконки — Lucide (`i-lucide-*`), набор стоит пакетом и попадает в сборку. Другой набор — сначала
  поставить его пакет `@iconify-json/<набор>`, иначе иконки грузятся с внешнего сервера Iconify.
- Логика — в слоях (composables, utils), в экранах только разметка и вызовы. Тогда смена
  UI-библиотеки — это переписать экраны, слои не трогать.

## API
- Запросы к бэкенду — только `useApi()` + `apiRequest()` из `core`: адреса, параметры и ответы
  типизированы. Никаких axios и ручных типов ответов. Данные публичной страницы (слой `page`) —
  `usePageRequest(key, api => api.GET('/api/page/…'))`: при рендере на сервере — через кэш слоя, ошибка
  API — страница ошибки с тем же кодом. Кэш пропускает только `/api/page/…`: другой адрес на сервере — 404.
- `layers/core/app/types/api.d.ts` генерируется `npm run api:types` — руками не править.
  Изменилось API бэкенда — перегенерировать и закоммитить вместе с правкой фронта.
- Ошибки — `ApiError`: `message` показывать пользователю как есть, `fieldMap` — под полями.
- Запросы к бэкенду — с таймаутом 60 секунд: в `useApi()` он уже есть, свой `$fetch` на сервере
  Nuxt — с `timeout: 60_000`. Без таймаута зависший бэкенд подвесит рендер страницы.
  Коды бэкенда: 422 — поля, 406 — сообщение бизнес-логики, 401 — вход, 500/0 — общий текст.

## Адреса сайта
- Корень сайта делят фронт и страницы из админки (слой `page`): адрес совпал — показывается
  страница фронта, бэкенду о ней знать не нужно. Новая публичная страница сайта — её адрес
  в `page.sitemapPageList` в `app.config` сайта, иначе её не будет в `sitemap.xml`.

## Токены
- Access — только в памяти (`useAccessToken()`), refresh — только в httpOnly-куке, её ставит
  бэкенд. Вход — из браузера прямо в API. Никогда не класть токены в localStorage.
- Страницы кабинета — под `/lk`: они рендерятся только в браузере (`routeRules` в `nuxt.config.ts`
  слоя `user`) и закрыты `definePageMeta({ middleware: 'auth' })`.

## Стиль
- TypeScript везде. Composables — `useX`, компоненты — PascalCase, файлы utils — kebab-case.
- Нейминг как на бэкенде: без сокращений, bool — `is_`/`isX`, списки — `List`.
- Поля запросов и ответов API — как в бэкенде (snake_case), не переименовывать.
- Комментарии и документация — на русском, объяснять «почему», а не «что».
