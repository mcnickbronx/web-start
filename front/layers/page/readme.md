# Слой page
Как устроен слой · 09.10.2026

Страницы сайта и блог из админки: рубрики, статьи, отдельные страницы вроде «О компании»,
SEO и `sitemap.xml`. Пара к модулю `page` бэкенда: тексты пишутся в админке, сайт получает
готовый HTML. Зависит только от `core`.

## Адреса

| Адрес | Что показывает |
|---|---|
| `/blog` | общая лента всех рубрик, по 12 статей, дальше — `?page=2`; статей нет — 404 |
| `/{рубрика}` | описание рубрики и её лента |
| `/{рубрика}/{статья}` | статья |
| `/{страница}` | отдельная страница из админки |
| `/sitemap.xml` | карта сайта |
| `/media/…` | картинки из админки — пересылаются с бэкенда |

- **Что лежит по адресу в корне** — рубрика или страница, — бэкенд отвечает одним запросом.
- **Страницы фронта** (`/login`, `/lk`, `/blog`) проверяются раньше адресов из админки: адрес
  совпал — показывается страница фронта. Бэкенду о страницах сайта знать не нужно.
- **Статью перенесли в другую рубрику** — по старому адресу постоянный редирект на новый,
  с теми же параметрами: ссылки и закладки не ломаются, метки рекламы (`utm_*`, `yclid`)
  доходят до заявки.
- **Старый адрес** — сменили слаг в админке или адрес остался от прежнего сайта: тоже постоянный
  редирект с теми же параметрами. Список — в админке, «Страницы → Редиректы», как он
  пополняется — [модуль page бэкенда](../../../back/app/page/readme.md#редиректы). О редиректе
  сервер сайта спрашивает, только когда рисует 404, — живые страницы лишнего запроса не делают.
  Поэтому редирект срабатывает при открытии адреса — поисковик, закладка, ссылка извне или из
  текста статьи. Переход по `NuxtLink` (меню, шапка) идёт в браузере и на старом адресе покажет 404:
  такие ссылки правят в коде сайта.

## Для поисковиков

- **Открыт ли сайт для поиска — `NUXT_PUBLIC_SITE_INDEXED`.** По умолчанию закрыт: `robots.txt`
  запрещает всё, на всех ответах `X-Robots-Tag: noindex, nofollow` — robots.txt лишь просит
  не обходить сайт, а уже найденные страницы поисковик убирает по noindex. Открыть при запуске —
  `NUXT_PUBLIC_SITE_INDEXED=true` в `.env` на сервере и пересоздать контейнер, пересборка не нужна.
  Так забытый dev-сайт не попадёт в поиск дублем боевого.
- **`robots.txt` открытого сайта** — служебные адреса (`/_page-api/`, `/lk`) мимо
  поиска, `Clean-param` склеивает у Яндекса страницы с метками рекламы (utm, yclid, gclid)
  с самой страницей, адрес карты сайта. Скрипты и стили не закрыты: без них поисковик не увидит
  страницу такой, какой её видит человек. Свой файл целиком — `public/robots.txt` сайта:
  он важнее маршрута слоя, но `NUXT_PUBLIC_SITE_INDEXED` им уже не управляет — dev-сайт отдаст то же, что боевой.

- **Всё рендерится на сервере:** поисковик получает готовый HTML со статьёй, заголовком
  и описанием.
- **Нет страницы — код 404, бэкенд не ответил — 502.** Пустую страницу с кодом 200 поисковик
  проиндексировал бы как настоящую. Поэтому и лента `/blog` без единой статьи — 404: она есть
  на каждом сайте, в том числе на сайте без блога.
- **На каждой странице** — заголовок и описание из SEO-полей админки, canonical, Open Graph
  с обложкой (превью ссылки в мессенджерах). «Показывать поисковикам» выключено — `noindex`.
- **canonical ленты и рубрики** — только адрес и номер страницы: `?utm_source=…` и прочие
  параметры — та же страница.
- **Пагинация — обычными ссылками** `?page=2`: поисковик обходит ленту без скриптов.
- **`sitemap.xml`** — два списка: страницы фронта из `page.sitemapPageList` в `app.config` сайта
  и всё открытое для индексации из админки. Один адрес в обоих — одна запись. Бэкенд не ответил —
  в карте остаются страницы фронта: неполная карта лучше ошибки.
- **`page.sitemapPageList` сайта дописывается к списку движка, а не заменяет его** — так сливаются
  массивы `app.config` всех слоёв. В движке поэтому только `/`; есть блог — сайт дописывает `/blog`.

## Кэш на сервере сайта

Страницы рендерятся на сервере Nuxt, и за данными к API ходит он, а не браузер посетителя.
Для Traefik все эти запросы — с одного адреса, контейнера сайта, и делят один лимит на IP
(около 150 одновременных): без кэша сотня посетителей блога разом упёрлась бы в него.

Поэтому данные страниц слой берёт через кэш: `usePageApi()` на сервере ходит в свой маршрут
`/_page-api/…` внутри процесса Nuxt — без сети и Traefik, в браузере — прямо в API.

- **Минута свежести, дальше — без ожидания.** Ответ свежий 60 секунд (`PAGE_CACHE_SECONDS`
  в `server/utils/page-cache.ts`), потом посетитель сразу получает сохранённое, а сервер берёт
  свежее у бэкенда в фоне. Правка в админке — и публикация, и снятие с публикации — появляется
  на сайте в пределах минуты.
- **Одновременные запросы одного адреса** бэкенд получает одним запросом.
- **Что сохраняется** — ответ о странице: есть она (200) или нет (404). Сохранённый 404 и убирает
  с сайта снятую статью: без него кэш отдавал бы её вечно.
- **Сбой не сохраняется** — лимит Traefik (429), ошибка или молчание бэкенда (5xx): сайт отдаёт
  последнее сохранённое, пока бэкенд не поднимется.
- **Не больше 1000 ответов** — старые вытесняются. Без предела перебор адресов и номеров
  страниц раздул бы память сервера сайта. Параметры, которых API страниц не знает (`?x=1`,
  метки рекламы), отбрасываются: иначе каждый такой адрес шёл бы мимо кэша к бэкенду.
- **Только GET и только `/api/page/…`.** Формы, вход, кабинет идут мимо кэша. Путь, уводящий
  из `/api/page/` (`%2e%2e`), — 404: иначе через кэш можно было бы достать другое API.
- `sitemap.xml` — через тот же кэш.
- Кэш — в памяти контейнера сайта: после перезапуска первые запросы идут к бэкенду.

## Что стоит знать

- **Адрес сайта — `NUXT_PUBLIC_SITE_URL`**, на сервере обязательно: от него canonical, Open Graph
  и карта сайта. Подробно — [слой core](../core/readme.md#seo-по-умолчанию).
- **Картинки.** В статьях адреса `/media/…` от корня сайта, а файлы лежат на бэкенде — слой
  пересылает их через сервер Nuxt. Только чтение и только внутри `/media/`: путь, уводящий
  выше (`/media/%2e%2e/…`), — 404, иначе сайт стал бы прокси к API и админке бэкенда.
  На сервере быстрее отдать `/media` прокси (Traefik) прямо в контейнер файлов бэкенда, минуя Node.
- **Даты — по Москве, явно.** Сервер в контейнере живёт в UTC, браузер — в поясе посетителя,
  и дата публикации после полуночи разошлась бы между ними. Другой пояс — в `app/utils/format-date.ts`.
- **Текст статей** — HTML, собранный и очищенный бэкендом. Оформление — классы `prose`
  плагина `@tailwindcss/typography`.
- **Свой вид** (всё, что сайт может поменять, — [таблица](../../readme.md#что-сайт-может-поменять)) — файл с тем же именем в `app/components/` сайта: лента целиком `PageBlog`,
  карточки `PageFeed`, статья и отдельная страница `PageArticle`, меню рубрик `PageCategoryMenu`.
  Ленту `PageBlog` и `PageFeed` получают в свойстве `result`, её тип — `PageFeedList`: сгенерированное
  имя схемы API меняется при переименованиях на бэкенде, а этот тип — нет.
  Страницы слоя не перекрывать: в них логика — данные, SEO, 404 и редиректы.
- **Данные для своей страницы** — как в страницах слоя: `usePageRequest(key, api => api.GET('/api/page/…'))`.
  При рендере на сервере запрос идёт через кэш, ответ с ошибкой — страница ошибки с тем же кодом:
  нет данных — 404, бэкенд не ответил — 502. Сам клиент с кэшем — `usePageApi()`, отдельно он нужен редко.
- **Проверить редирект `curl`** — с `-H 'Accept: text/html'`: без него Nuxt узнаёт `curl` и вместо
  страницы 404 отдаёт JSON, а редирект живёт как раз в странице 404.
- **Тексты ленты и число статей на странице** — в `app/app.config.ts` сайта:
  `page: { blogTitle, blogDescription, feedRow }`.

## Шпаргалка

- `/blog`, `/{рубрика}`, `/{рубрика}/{статья}`, `/{страница}`, `/sitemap.xml`, `/robots.txt`.
- Открыть сайт для поиска — `NUXT_PUBLIC_SITE_INDEXED=true`, по умолчанию закрыт.
- На сервере — `NUXT_PUBLIC_SITE_URL`.
- Новая публичная страница сайта — её адрес в `page.sitemapPageList` в `app.config` сайта; есть блог — и `/blog`.
- Нет данных — 404 или 502, а не пустая страница.
- Старый адрес — 301 на новый: «Страницы → Редиректы» в админке; при смене слага пишется сам.
- Данные своей страницы — `usePageRequest(…)`: на сервере через кэш, правка в админке — на сайте в пределах минуты.
