# Ядро проекта
Общее для всех модулей · 05.10.2026

`core` — не модуль с фичей, а общий слой: то, чем пользуются все остальные модули.
Своих моделей, админки и эндпоинтов у него нет, в Swagger и в админке он не виден.

Правило простое: переиспользуемое между модулями — в `core`, настройка конкретного
проекта (какие приложения, какие ключи, как запускается) — в `project`.

## Что здесь лежит

| Что | Зачем |
|---|---|
| Общие схемы ответов | типовые ответы и формат ошибки 422 в Swagger |
| Пагинация и сортировка | один формат списков на весь API |
| Обработка ошибок | любая ошибка выходит наружу в одном формате, на русском |
| Переводы ошибок валидации | сообщения Pydantic по-русски |
| Подключение к базе для API | асинхронный доступ к тем же таблицам, что у Django |
| Генератор моделей | `models_async.py` из Django-моделей |
| Фоновые задачи | брокер и правила запуска задач |
| Мост для админки | асинхронный сервис API вызывается из админки и команд |
| Письма | отправка по шаблону |
| Браузер посетителя | User-Agent для людей — «Chrome, Android, телефон»: в заявках и в списке сессий |
| Фильтр с поиском в админке | `admin_filters.py`: фильтр списка по связи с большим справочником, с подсказками по мере набора |
| Общее для админки | `static/core/admin.js` и `.css`: панель фильтров сворачивается щелчком по «Фильтр», курсор сразу в поиске подсказок |
| Свой `runserver` | админка и API на одном порту локально |
| Основа тестов API | клиент FastAPI на настоящей базе, токен пользователя, ожидание задач |

## Списки

Списки с пагинацией в API выглядят одинаково: `{"items": [...], "total": {"count": N}}`.
Фронт разбирает их одним и тем же кодом, и не приходится каждый раз договариваться
о названиях полей. Короткие списки без пагинации — справочники (`/info`), сессии
пользователя — отдаются просто массивом.

```python
from core.pagination import ListOut, Pagination, paginate, sort_queryset

@router.get("/list", response_model=ListOut[ProductOut], summary="Список товаров")
async def product_list(pagination: Pagination, sort: str = "-id"):
    queryset = sort_queryset(Product.all(), sort, ["id", "title", "price"])
    return await paginate(queryset, pagination)
```

Страница задаётся параметрами `page` и `row`, по умолчанию 20 записей, больше 1000
за раз отдать нельзя. Номер страницы — до 10 000: дальше `422`, а не ошибка базы на огромном
смещении. Каждая запись получает `row_number` — сквозной номер по всей
выборке, а не по странице: на второй странице нумерация продолжается, а не начинается
заново. Поле должно быть объявлено в схеме ответа, иначе его не будет видно.

Сортировка приходит параметром `sort`, префикс `-` — по убыванию. Сортировать можно
только по полям, которые эндпоинт разрешил явно: по остальным приходит `406` с перечислением
допустимых. Это не придирка — сортировка уходит прямо в базу, и произвольное поле в ней
означает произвольный запрос к любой связанной таблице.

При равных значениях записи идут по `id`, новые первыми. Без второго ключа база отдаёт
равные записи в любом порядке, и он может меняться от запроса к запросу: статьи с одной датой
на границе страниц ленты то повторялись бы на соседней странице, то не попадали ни на одну.

Каждый список — два запроса к базе: сначала общее количество, потом сама страница.
Про `count` стоит помнить на больших таблицах: он считает все строки, подходящие под фильтры.

## Ошибки

Наружу всё выходит в одном виде — объект с полем `message` на русском. Разбирать
формат по коду ответа фронту не нужно.

- Бизнес-ошибка — `406` и текст, который можно показать пользователю.
- Ошибка валидации — `422`: в `message` все проблемы одной строкой, в `full_error` —
  разбор по полям. Переводы подставляются по коду ошибки Pydantic, а не по английскому
  тексту: коды между версиями стабильны, тексты меняются. Незнакомый код оставит
  английское сообщение — значит, его стоит добавить в переводы.
- Ошибка поля, которую нашёл сервис, а не схема (обязательное по настройкам, «телефон или
  email»), — тоже `422` в том же виде: `raise field_error({"phone": "Текст"})`. Сайт покажет
  её под полем, а не общим сообщением. `406` — для того, что к полю не относится.
- Запрошенная запись не найдена — `404` «Не найдено». Имя модели наружу не уходит:
  по тексту ошибки нельзя изучать устройство базы.
- Всё остальное — `500` «Внутренняя ошибка сервера». Подробности не показываем,
  но трейсбек попадает и в stdout, и в журнал, см. [модуль «Журнал»](../log/readme.md).

## База для API

Подключение Tortoise собирается из настроек Django: база одна, описана в одном месте,
разъехаться настройкам негде. Время везде UTC — и Django, и API пишут в базу одинаково.

У каждого процесса API свой пул соединений (`API_DB_POOL_SIZE`). Ограничение, о котором
легко забыть при масштабировании: **число процессов × размер пула** не должно превышать
`max_connections` PostgreSQL, иначе новые процессы начнут получать отказ от базы.

Генерация `models_async.py` описана в [architecture.md](../../docs/architecture.md).
Здесь достаточно одного: генератор не угадывает.
Незнакомое поле — ошибка команды, а не молчаливая подмена на что-то похожее. Модели
сторонних приложений не генерируются, они остаются только на стороне Django.

## Фоновые задачи

Задача объявляется в `<module>/tasks.py` и вызывается из сервиса. Вызов не ждёт
результата: основное действие завершается, задача уходит в очередь.

Объявлять задачу — только в `tasks.py`: воркер знает задачи из этих файлов. Объявленную
в другом месте локально, без Redis, выполнит сам процесс API, а воркер на сервере может её
не найти — и поломка видна только там.

```python
@broker.task                       # tasks.py модуля, broker — из core.broker
async def send_report(user_id: int) -> None: ...

await send_report.kiq(user.id)     # в сервисе
```

Работает это двумя способами, в зависимости от того, задан ли `REDIS_URL`:

- **Задан** — задачи складываются в Redis, их разбирает отдельный процесс-воркер.
  Так на сервере: если API перезапустят, очередь не пропадёт. Задача уходит из очереди,
  только когда выполнена: если воркер упал посреди неё, через 10 минут её заберёт другой.
  Поэтому задача может выполниться дважды и должна это спокойно переживать — повторное
  письмо с кодом не беда, повторное списание денег недопустимо.
- **Не задан** — задача выполняется тут же, в процессе API. Локально это удобно,
  Redis и воркер не нужны. Но задача при этом живёт в том же процессе: при остановке он
  дожидается начатых задач, а если его убили или задача висит дольше, чем ждёт docker, —
  потеряли.

Туда уносится то, чей результат не нужен пользователю сразу (письма, отправка данных
во внешние системы), и то, что грузит процессор или базу (отчёты, выгрузки). Процесс API
обслуживает много запросов сразу, и тяжёлый расчёт в нём останавливает не один запрос,
а все. А вот ждать внешний сервис, ответ которого нужен пользователю сейчас, можно прямо
в запросе через `aiohttp`: асинхронное ожидание процесс не занимает — ради этого API
и асинхронный (см. [замер](../../docs/benchmark.md)).

## Асинхронный сервис из админки

Сервисы API асинхронные и ходят в базу через Tortoise, а админка и команды `manage.py`
синхронные: асинхронную функцию напрямую они вызвать не могут. Чтобы действие, нужное
и в API, и в админке, не писать дважды на двух ORM, у сервиса есть синхронный вызов
`.sync(...)`. Код сервиса один.

### Как вызвать

Сервис в `services.py` модуля помечается декоратором — больше в нём ничего не меняется:

```python
from core.bridge import with_sync

@with_sync
async def cancel_order(order_id: int, reason: str) -> None:
    ...  # Tortoise, задачи, HTTPException(406, "...") — как в любом сервисе API
```

API и задачи вызывают его как обычно: `await services.cancel_order(order.id, "...")`.

**Из админки — действием над выбранными записями.** Основной способ: менеджер отмечает
записи и выбирает действие в списке.

```python
from django.contrib import admin, messages
from fastapi import HTTPException

class OrderAdmin(admin.ModelAdmin):
    readonly_fields = ["status"]   # статус — только действием: у смены есть последствия
    actions = ["cancel"]

    @admin.action(description="Отменить заказ")
    def cancel(self, request, queryset):
        for order_id in queryset.values_list("id", flat=True):
            try:
                services.cancel_order.sync(order_id, f"Отменён менеджером {request.user}")
            except HTTPException as exc:   # бизнес-ошибка сервиса — сообщением в админке
                self.message_user(request, f"Заказ №{order_id}: {exc.detail}", messages.ERROR)
```

Рабочий пример — действие «Отправить письмо ещё раз» в админке заявок (`form/admin.py`).

**Из админки при сохранении формы** — только если без обычного поля в форме не обойтись.
Вызов — после коммита: до него Tortoise не видит того, что админка сохранила.

```python
from django.db import transaction

def save_model(self, request, obj, form, change):
    super().save_model(request, obj, form, change)
    if "status" in form.changed_data:
        transaction.on_commit(lambda: services.after_status_change.sync(obj.id))
```

Отказать здесь сервис уже не сможет — запись сохранена. Проверку «можно ли» тогда
делают в `clean()` формы.

**Из команды `manage.py`** — так же, `.sync(...)`:

```python
class Command(BaseCommand):
    def add_arguments(self, parser):
        parser.add_argument("order_id", type=int)

    def handle(self, *args, **options):
        services.cancel_order.sync(options["order_id"], "Отменён командой")
```

В `manage.py shell` — тоже: `services.cancel_order.sync(5, "проверка")`.

### Когда это нужно, а когда нет

- **Проверки и расчёты без базы** — обычная функция, её зовут обе стороны без всякого
  моста (пример — проверка полей заявки в модуле «Заявки»).
- **Простая правка данных** — тексты, названия, настройки — админка делает сама, через Django.
- **Действие с последствиями** — письмо, смена остатков, запись в историю — и **постановка
  фоновой задачи** из админки: асинхронный сервис через `.sync(...)`. Поле с такими
  последствиями в админке только для чтения, меняется оно действием.

В `save()` и сигналы последствия не кладём: из API они не вызываются, а из админки
сработали бы и при правке скриптом.

### Как работает и что помнить

Админка живёт в одном процессе с API — и локально, и на сервере, — и вызов идёт через
уже открытые соединения API. В командах `manage.py` своего API в процессе нет —
мост на время вызова сам открывает соединение с базой и закрывает его после. Для нажатия
кнопки это незаметно, а для тысяч вызовов подряд не годится: массовое — в фоновую задачу.

- Передавать номер записи, а не объект из админки: сервис работает со своей ORM.
- Общей транзакции с Django нет: если рядом сохраняли через Django — вызывать после коммита.
- Без Redis задачи, которые поставил сервис, выполняет тот же процесс. Из админки их доделывает
  процесс API, и кнопка отвечает сразу. В команде `manage.py` мост их дожидается — иначе они
  оборвались бы вместе с вызовом, — поэтому команда завершается после отправки письма.
- Из асинхронного кода (API, задачи) — только `await`: `.sync()` там выдаст ошибку.

## Письма

Письмо собирается по шаблону из `templates/email/` модуля, который его отправляет. Папка
`email/` у всех модулей общая, поэтому имя шаблона — уникальное на проект. Текстовая версия
делается из того же HTML — писать два варианта руками не нужно. Название и адрес сайта
подставляются в шаблон сами, из настроек.

Отправлять только из задач. В эндпоинте почтовый сервер задержит ответ на всё время
соединения, а если он недоступен, вместе с письмом упадёт и основное действие —
регистрация или смена пароля.

Тексты писем — на русском, ссылки берут домен из `SITE_URL`, а не из запроса:
письмо не должно зависеть от того, с какого адреса пришёл пользователь.

## Локальный запуск

`manage.py runserver` здесь свой и перекрывает стандартный: стандартный про FastAPI
не знает и поднял бы только админку. Поэтому локально админка и API живут на одном
порту, и Swagger доступен сразу — `/api/docs`.

Команда только для разработки. На сервере — тот же `project/asgi.py` под uvicorn: в профиле light
админка и API одним процессом, в full админка — отдельным, см. [deploy.md](../../docs/deploy.md).

## Что класть в core, а что нет

Сюда — то, что нужно нескольким модулям и не зависит от предметной области проекта:
формат ответа, обработка ошибки, отправка письма, постановка задачи.

Не сюда — логика конкретной области, даже если её «наверное, переиспользуют».
Пока пользователь один, она живёт в своём модуле. Общий слой, в котором лежат чужие
правила, перестаёт быть общим: его нельзя взять в следующий проект целиком.

## Шпаргалка

- Список — через пагинацию и сортировку из `core/pagination.py`, в схеме нужно `row_number`.
- Сортировка — только по разрешённым полям, остальное `406`.
- Бизнес-ошибка — `406` с текстом для пользователя; `404` и `500` подробностей не выдают.
- Новый код ошибки валидации по-английски — добавить перевод в `core/translations.py`.
- В `tasks.py` — письма, отправка во внешние системы, тяжёлые расчёты и отчёты; внешний вызов, ответ которого нужен сразу, — в запросе через `aiohttp`.
- Процессы API × размер пула ≤ `max_connections` базы.
- Действие и в API, и в админке — один асинхронный сервис с `with_sync`, в админке — `.sync(...)` из кнопки, не из `save()`.
