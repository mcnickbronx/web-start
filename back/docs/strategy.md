# Стратегия разработки новых проектов
Выводы из замера производительности · 22.10.2026

На чём делать новые проекты, как расти под нагрузкой и когда менять стек. Основано
на замере — [benchmark.md](benchmark.md): там цифры, здесь
решения, которые из них следуют.

## Стек по умолчанию — этот шаблон

Django для админки, моделей и миграций, FastAPI для API.

Почему:
- **Админку Django заменить нечем.** Ни в Node.js, ни в Go нет ничего похожего:
  автоматическая по моделям, с правами, фильтрами и вложенными формами. Писать такую
  самим дороже, чем держать вторую ORM.
- **Запас по нагрузке в 2–3 раза над Django.** На одном ядре шаблон держит ~700–800
  активных пользователей, Django — ~300. Главное — страницы с внешними сервисами:
  Django на них обваливается, шаблон открывает их почти за время ответа самого сервиса.
  Если долгие вызовы отдавать из кэша, как велят правила ниже, обвала у Django не будет,
  но разница останется: шаблон тратит на запрос вдвое меньше процессора. А вызовы,
  которые не закэшируешь, — оплата, запрос под конкретного пользователя — страницы
  шаблона не обрушат.
- **Этого запаса кабинетам хватает.** Раньше упрёмся в базу, а базе язык не важен.
  Node.js и Go быстрее, но их запас на обычных проектах съедает база.

Чего не хватало до первого магазина или кабинета — истории изменений, общего клиента для внешних
сервисов, фильтров списков, — теперь есть: [карта модулей](../../readme.md#из-чего-собирается-проект).

## Что брать под какой проект

- **Кабинет, CRM, магазин** — бизнес-логика, админка, интеграции: шаблон.
- **Маленький внутренний инструмент** на несколько человек: тоже шаблон. Один стек
  на все проекты проще, чем выгода от облегчённого варианта: одни правила, один деплой,
  код переносится между проектами.
- **Контентный сайт** — блог, каталог, лендинги: фронт на Nuxt, бэкенд на шаблоне.

## Правила разработки

Из того, что показал замер. Часть уже закреплена в [CLAUDE.md](../CLAUDE.md).
- **В API — только асинхронный код.** FastAPI с обычным синхронным кодом держит столько же,
  сколько Django: выигрыш даёт асинхронность, а не название фреймворка.
- **Долгое и тяжёлое — в фоновые задачи.** Отчёты, выгрузки, письма, отправка во внешние
  системы. Долгий ответ внешнего сервиса, который нужен на странице, — из кэша, который
  обновляет фоновая задача.
- **Страница — поменьше запросов и без цепочек.** Каждый шаг цепочки ждёт предыдущий,
  и под нагрузкой замедления складываются. Ответы сжимать, дубли убирать.
- **Большие таблицы** — постраничная выдача без точного подсчёта всех строк.
- **База — главный потолок.** Индексы и число запросов на страницу важнее выбора языка.

## Как расти под нагрузкой

По шагам, от дешёвого к дорогому. Следующий шаг — только когда предыдущий исчерпан.

1. **Ускорить запросы и страницы.** Найти тяжёлые запросы к базе, убрать лишние со страниц,
   закэшировать долгие ответы. Дешевле всего и помогает всем сразу.
2. **Добавить ядер.** Шаблон почти удваивается со вторым ядром. На сервере с базой — делить
   примерно поровну: 4 ядра — 2 приложению, 2 базе.
3. **Вынести базу на отдельный сервер, приложение растить вширь.** По скорости это почти
   то же, что один сервер побольше, но тяжёлые отчёты перестают тормозить API, а второй
   сервер приложения почти удваивает его. Имеет смысл, когда проектов много или отчёты
   мешают сайту.
4. **Вынести нагруженную часть в отдельный сервис** — одну конкретную, а не весь проект
   (см. «Node.js и Go»).
5. **Переписывать проект на другой язык** — в самую последнюю очередь.

Как понять, где мы сейчас:
- **Запросов в секунду в самую загруженную минуту дня** — по логам. Один активный
  пользователь даёт ~0,6 запроса в секунду. Десятки в секунду — запас огромный.
- **Процессор базы на один запрос к API** — меньше ~2 мс: упирается приложение, помогут
  ядра приложению; больше — упирается база, ускорять запросы. Как измерить —
  в разделе «Как оценить свою нагрузку» отчёта.

## Замер на самом проекте

Пределы в отчёте получены на лёгких тестовых запросах. У настоящего проекта они будут ниже.
Перед запуском и перед ожидаемым ростом — дать нагрузку на само приложение. Скрипт
для этого в планах ([todo.md](todo.md)), на чём ломался замер — в разделе «Если мерить
снова» отчёта. Это дешевле, чем узнать предел от пользователей.

## Node.js и Go

Проекты делаем на шаблоне. Node.js на замере держит на ядро вдвое больше FastAPI, Go —
впятеро, но админки уровня Django нет ни там, ни там, а общая логика расходится на два
языка. Вспоминать о них стоит, только когда отдельная часть проекта — публичное API,
приём вебхуков — упрётся в процессор приложения, а не в базу, и шаги 1–3 уже сделаны.
Тогда её выносят в небольшой сервис рядом с шаблоном, на той же базе.

## Шпаргалка

- Новый проект — на шаблоне: нужное взять из [карты модулей](../../readme.md#из-чего-собирается-проект).
- В API только асинхронное, тяжёлое — в фон, база — главный потолок.
- Рост: запросы → ядра → отдельный сервер базы → отдельный сервис для нагруженной части
  → переписывание.
- Перед запуском и ростом — нагрузочный тест на самом проекте.
