# Модуль «Журнал»
Как устроен модуль · 21.09.2026

Журнал событий проекта: что произошло, когда и в каком модуле. Записи видны в админке,
в разделе «Журнал», и переживают перезапуск контейнеров — в отличие от `docker compose logs`,
где история ограничена тем, что docker ещё не выбросил.

Журнал заполняется только тем, что написали сами: логи Django, uvicorn и Tortoise
в базу не попадают. Они по-прежнему идут в stdout и читаются через `docker compose logs`.

## Как писать в журнал

В начале файла — логгер, дальше обычные вызовы `logging`:

```python
import logging

logger = logging.getLogger(__name__)

logger.info(f"Заявка {order.id} подтверждена пользователем {user_id}")
```

Вызов одинаков во всём проекте: в асинхронном эндпоинте, в сервисе, в фоновой задаче,
в админке и в команде `manage.py`. Никакого `await` не нужно — запись попадает в очередь
в памяти, а в базу её пишет отдельный поток. Поэтому логирование не задерживает ответ
клиенту, даже если база отвечает медленно.

Имя логгера (`logger_name` в админке) — это имя модуля: `order.services`, `user.tasks`.
По нему в журнале удобно фильтровать.

## Какой уровень выбирать

| Вызов | Когда |
|---|---|
| `logger.debug(...)` | подробности для разбора, в журнал не попадает |
| `logger.info(...)` | значимое событие: заявка создана, статус изменён, импорт завершён |
| `logger.warning(..., exc_info=True)` | некритичное не получилось: письмо не ушло, аналитика не записалась |
| `logger.exception(...)` | о таком надо узнать сразу: внешний сервис отвечает мусором, импорт сломался |

`exc_info=True` и `logger.exception(...)` добавляют к записи трейсбек — без них в журнале
будет только текст сообщения. Разница между ними одна: `exception()` всегда пишет уровень
Error, а `warning(..., exc_info=True)` оставляет Warning.

Бизнес-ошибки в журнал не пишем: ответ `406` с понятным текстом — это обычный ход работы,
а не событие. Если логировать каждый отказ, настоящие ошибки в журнале потонут.
Необработанные ошибки (`500`) попадают в журнал сами.

## Что журнал не гарантирует

Запись в журнал — «выстрелил и забыл». Она потеряется, если процесс убили жёстко
(`docker kill`, нехватка памяти) или если база в этот момент недоступна. Основное
действие при этом выполняется нормально, и клиент ничего не замечает.

Поэтому **в журнал идёт только то, что можно потерять**. Если запись терять нельзя —
списание денег, согласие пользователя, история статусов, которую покажут заказчику, —
это не лог, а данные: обычная модель, обычная запись в запросе, падение при ошибке.

Ещё две вещи, о которых стоит знать заранее:

- **Порядок между процессами приблизительный.** У каждого процесса своя очередь, поэтому
  записи из разных воркеров перемешиваются в пределах доли секунды. Внутри одного запроса
  порядок сохраняется.
- **Нагрузку на базу журнал не убирает, а переносит.** Пятьдесят записей за запрос — это
  пятьдесят вставок, просто не в ответе клиенту. Логировать в цикле по всем строкам
  импорта не стоит: одна запись с итогом полезнее тысячи с подробностями.

## Уборка

Журнал растёт без ограничения, само ничего не удаляется. Уборка — командой:

```
python manage.py clear_log --days 90
```

Она в расписании `project/crontab`, раз в сутки. Сколько хранить — решать по проекту: 90 дней
хватает, чтобы разобрать жалобу «месяц назад не пришло письмо».

Записи можно удалять и из админки, выделив их в списке. Редактировать нельзя: журнал,
который можно исправить, журналом не является.

## Шпаргалка

- Писать: `logger = logging.getLogger(__name__)`, дальше `logger.info(...)`, без `await`.
- Нужен трейсбек — `exc_info=True` или `logger.exception(...)`.
- Смотреть: админка → Журнал, фильтры по уровню и модулю, поиск по тексту.
- В журнал — только то, что можно потерять. Остальное — обычная модель.
- Уборка: `manage.py clear_log --days 90`, в `project/crontab`.
