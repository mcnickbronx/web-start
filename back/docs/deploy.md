# Деплой

Техническая заметка для разработчика · 25.10.2026

Проект разворачивается на сервере с нашей инфраструктурой — [infra](https://github.com/mcnickbronx/infra):
HTTPS и распределение запросов по контейнерам делает Traefik, Postgres работает на хосте,
у каждого проекта свои лимиты памяти и процессора, новую версию сервер выкладывает сам.
`compose.yml` написан под неё. Её команды (`project-db-env`, `project-deploy`) описаны ниже
как есть, а чем их заменить на своём сервере — в разделе [«Что нужно от сервера»](#что-нужно-от-сервера).

## Как разложено на сервере

```
Интернет ─► Traefik (HTTPS, сертификаты, лимиты с одного адреса)
              ├── /static/, /media/  ─► files  nginx, только чтение
              └── остальное          ─► app    uvicorn: /api → FastAPI, остальное → Django

cron — задачи по расписанию (ниже). PostgreSQL — на хосте, в контейнерах его нет.
```

Точка входа везде одна — `project/asgi.py`, как локальный `runserver`: запросы делятся
по адресу до Django, синхронный код админки идёт в отдельном потоке. Профиль — `COMPOSE_PROFILES`
в `.env` — решает, сколько процессов и где фоновые задачи (письма):

- **light** — админка, API и задачи одним процессом `app`. Три контейнера, ~200 МБ: контентный
  сайт. Цена: письмо, которое отправлялось в момент перезапуска, может не уйти — у заявки
  останется статус «ждёт отправки», её видно в админке.
- **full** — для кабинетов и магазинов. API — `app-full`, админка — отдельным процессом `admin`
  (Traefik отправляет туда `/admin`): тяжёлая выгрузка в админке не тормозит API, нехватка
  памяти роняет только админку. Задачи — через Redis и воркер (`redis`, `worker`): очередь
  переживает перезапуск. В `.env` к профилю — `REDIS_URL=redis://redis:6379/0`; в light этот
  адрес приложение не видит, даже если он остался в `.env`. Почему так —
  в описании [точек входа](../app/project/readme.md).

Без `COMPOSE_PROFILES` поднимутся только `files` и `cron`. Сменить профиль у работающего проекта —
остановить сервисы старого: `--profile full stop app-full admin worker redis` (или `--profile light stop app`),
затем `up -d`.

Папка проекта — `/srv/projects/<проект>/web`: `.env`, `compose.yml` и папки, куда пишет
приложение: `media/`, `private/`, `static/`. Доступ к базе проекта тоже в `.env`: его кладёт
туда администратор сервера командой инфраструктуры `project-db-env` (ниже, «Первый запуск»).

Все контейнеры — из одного образа (зависимости и код) и отличаются командой запуска.
Образ собирает CI (`.github/workflows/back.yml`) на каждый push в `dev`, `main` и ветки `try-*` и кладёт
в `ghcr.io/<владелец>/web-start-back` под двумя именами: веткой (`:dev`) и полным хешем коммита.
Образ версии (`:v3.0.0`) — запуском CI на теге при выпуске ([«Как выпустить версию»](../../readme.md#как-выпустить-версию)).
Сервер выкладывает тот образ, что указан в `DEPLOY_IMAGE` его `.env`, — см. «Выкладка».
`compose.yml` тоже едет в образе: на сервер его руками не кладут.

## Что нужно от сервера

На сервере с [infra](https://github.com/mcnickbronx/infra) всё перечисленное ниже уже есть.
На другом сервере `compose.yml` как есть не поднимется: он рассчитывает на то, что там уже есть:

- **Traefik** с входом `websecure` (HTTPS и сертификаты) и middleware `login-ratelimit`
  из файла настроек — строгий лимит на вход и формы (ниже, «Ограничение частоты запросов»).
  Другой прокси — те же правила по адресам из `labels` в `compose.yml`, руками.
- **Сеть** `proj-<COMPOSE_PROJECT_NAME>`, к которой подключён Traefik: `docker network create`
  заранее — `compose.yml` её не создаёт.
- **Файл `/srv/infra/compose/base.yml`** — общие настройки контейнеров, на них ссылаются `extends`.
  `hardened`: `restart: unless-stopped`, `no-new-privileges`, без лишних прав Linux (`cap_drop`),
  лимиты процессов и открытых файлов. `hardened-strict` — то же и `cap_drop: [ALL]`. Положить
  свой файл с этими двумя сервисами или убрать строки `extends` — защита станет слабее, но всё
  запустится.
- **PostgreSQL** — доступ в `.env` (`DB_*` или `DEV_DB_*`) вписать самому.
- **Папки** `media/`, `private/`, `static/` рядом с `compose.yml` — с записью для пользователя 1000:
  приложение в контейнере работает от него. Иначе docker создаст их от root, и запись в них упадёт.
- **Выкладка** — у нас её делает сервер (ниже, «Выкладка»). Без неё — руками в папке проекта,
  `compose.yml` — из `back/` того же коммита, что и образ:
  ```bash
  docker compose pull
  docker compose run --rm deploy    # модели для API, миграции, статика
  docker compose up -d
  ```

## Кто что делает

- **Код** — git: push в `dev` выкладывает dev-проект. Боевой стоит на версии (или хеше коммита)
  из своего `.env` и переходит на новую, когда её сменят. Руками на сервер код не заливают.
- **`.env`** — пользователь проекта, в `web/` через SSH или SFTP.
- **Контейнеры** запускает автовыкладка. Посмотреть и вмешаться — тот, у кого на сервере
  есть Docker (`docker_users` инфраструктуры; это root на сервере): `docker compose ps`,
  `logs` в папке проекта. Или администратор: `sudo project-compose <проект> ...`.
- Код в образе принадлежит root — приложение его не поменяет. Пишет оно в `media/`, `private/`
  и `static/`: их автовыкладка создаёт с записью для группы проекта.

Команды `manage.py` на сервере запускаются в сервисе `cron`: у него нет адресов в Traefik,
и временный контейнер с командой не получит запросов сайта.

## Первый запуск

1. **`.env`** — из `.env.txt`, в `web/`. На сервере обязательно:
   - `DEPLOY_IMAGE=ghcr.io/<владелец>/web-start-back:dev` (dev-проект) или `:v3.0.0` (боевой) —
     версия, та же, что в `extends` фронта сайта (между выпусками — полный хеш коммита `main`, «Выкладка»);
   - `DEBUG=False`;
   - свои `SECRET_KEY` и `JWT_SECRET_KEY`, не короче 32 символов:
     `python -c "import secrets; print(secrets.token_urlsafe(50))"`;
   - `ALLOWED_HOSTS` — домен, `CSRF_TRUSTED_ORIGINS` — он же с `https://`,
     `CORS_ALLOWED_ORIGINS` — адреса фронта;
   - база — доступ в `.env` кладёт администратор сервера (пароль на экран не выводится,
     прежние строки заменяются). Так всё, что нужно приложению, видно в одном `.env`.
     **Прод:** `DEV=False` и `DB_*`:
     ```bash
     sudo project-db-env <проект>
     ```
     **Dev-сервер:** `DEV=True` и `DEV_DB_*`:
     ```bash
     sudo project-db-env <проект> DEV_
     ```
     Цена копии: сменил администратор пароль базы — повторить команду и пересоздать
     контейнеры (`docker compose up -d --force-recreate`), иначе API ответит 500. Любую правку
     `.env` контейнер видит только после пересоздания: `restart` читает старые значения;
   - `COMPOSE_PROJECT_NAME` — как папка проекта, `DOMAIN` — домен проекта;
   - `COMPOSE_PROFILES` — `light` (контентный сайт) или `full`; для full ещё
     `REDIS_URL=redis://redis:6379/0` — задачи через очередь и кэш справочников;
   - почта через SMTP и `SITE_URL` — адрес, на который ведут ссылки в письмах. Поправил SMTP —
     проверить командой из шага 4: `run` создаёт новый контейнер, и он читает новый `.env`; письма
     сайта пойдут с новыми значениями после пересоздания контейнеров.
2. **Автовыкладка** — администратор включает её проекту (`autodeploy: true` в инфраструктуре).
   Через минуту сервер выложит образ из `DEPLOY_IMAGE`: миграции, статика, запуск.
3. **Администратор сайта:** `docker compose run --rm cron python manage.py createsuperuser`.
4. **Проверка:** `https://<домен>/api/docs` — Swagger, `https://<домен>/admin/` — админка.
   Сертификат Traefik выпускает сам, если домен уже указывает на сервер. Почта — без заявки на сайте:
   `docker compose run --rm cron python manage.py sendtestemail <свой адрес>`. Письмо пришло — SMTP
   настроен; ошибка SMTP (адрес, порт, пароль) — сразу в консоли.

## Выкладка

**Dev-проект** идёт за веткой `dev` сам:

```bash
git push origin dev
```

Попробовать ветку на dev-проекте, не сливая её в `dev`: назвать `try-<что>` — CI соберёт и её
образ, `:try-<что>`, — и поставить его в `DEPLOY_IMAGE` dev-проекта. Сервер пойдёт за веткой,
пока стоит на ней, push в `dev` до него не доходит. Вернуть — `:dev` или `:<хеш>` нужного коммита.

**Боевой** стоит на одном коммите и обновляется, когда решат, а не от каждого push: новое
в движке не должно попадать на сайт без спроса. Обновить:
1. Выбрать версию (между выпусками — коммит `main`) с зелёным CI на вкладке Actions и прочитать
   CHANGELOG.md в корне репозитория: нет ли ручных шагов.
2. В `.env` сервера — `DEPLOY_IMAGE=ghcr.io/<владелец>/web-start-back:v3.0.0`. Образ с именем версии
   собирают при выпуске ([«Как выпустить версию»](../../readme.md#как-выпустить-версию)); такие есть
   с 3.0.0, у прежних версий — только полный хеш коммита. Между выпусками — полный хеш коммита `main`
   (`git rev-parse main`).
   Или администратор одной командой (на сервере infra 2.1.0 и новее) — можно сразу после выпуска,
   пока CI ещё собирает образ:
   ```bash
   sudo project-deploy <проект> to v3.0.0 --wait    # между выпусками — to <полный хеш> --wait
   ```
   Команда ждёт, пока образ появится в реестре (до 15 минут), выкладывает его и сама пишет тег
   в `DEPLOY_IMAGE`. Не дождалась — отказ, `.env` не тронут; сбой выкладки — работает прежняя версия
   с прежним `.env`.
3. Фронт сайта — на тот же тег `#v3.0.0` (или тот же хеш) в `extends`, после бэкенда (порядок —
   в [«Версиях»](../../readme.md#версии), шаги — в [«Обновить движок»](../../front/readme.md#обновить-движок)).

Дальше само:

1. **CI** (вкладка Actions на GitHub): проверки (`check`, модели для API, недостающие миграции)
   и тесты на Postgres той же версии, что на сервере. Красное — образа нет.
2. **Образ** с кодом и `compose.yml` — в ghcr.io, под именем ветки (на теге — версии) и полным хешем коммита.
3. **Сервер** каждые 15 секунд смотрит образ из `DEPLOY_IMAGE`: у dev-проекта новый появляется
   с каждым push, у боевого — когда сменили версию или хеш. Новый — забирает из него `compose.yml`,
   запускает сервис `deploy` (модели для API, миграции, статика) и пересоздаёт контейнеры,
   дожидаясь, пока приложение ответит на `/api/health`.

От push или смены версии до сайта — несколько минут. Упал любой шаг на сервере — возвращаются
прежние образ и `compose.yml`, сайт работает как был, а неудачная версия больше не пробуется:
исправить и выложить следующую. Об ошибке сообщает health-check сервера, причина —
`sudo journalctl -u project-deploy@<проект> -n 50` (у администратора).

Миграции — до перезапуска: несколько секунд старый код работает с новой схемой, поэтому
миграции должны быть совместимы с прежней версией. Откат схему не возвращает.

**Откат** — у боевого вернуть в `.env` прежний тег или хеш: сервер выложит его так же. Или администратор:
`sudo project-deploy <проект> to <прежний тег или хеш>` — то же одной командой, или
`sudo project-deploy <проект> rollback` — вернёт версию, которая стояла до последней выкладки,
и откаченная больше не выложится. Схему базы откат не возвращает.

## Сколько процессов ставить

В `.env`: `API_WORKERS` — процессы приложения (в light — админка и API вместе), в профиле full ещё
`ADMIN_WORKERS` — процессы админки и `TASK_WORKERS` — воркера. Сайту-визитке хватает одного
процесса приложения (~120 МБ).

Процессов API — по числу ядер, которые достаются проекту (обычно половина сервера):
асинхронный процесс и так занимает ядро целиком, лишний процесс на то же ядро не ускоряет,
а мешает (на замере два процесса на одном ядре держали ~600 активных против ~700 у одного).
См. [benchmark.md](benchmark.md).

Каждый процесс API держит свой пул соединений к базе (`API_DB_POOL_SIZE`, по умолчанию 10).
Правило: `API_WORKERS × API_DB_POOL_SIZE` плюс воркер и админка не должны превышать лимит
подключений проекта к базе (задаётся в инфраструктуре, по умолчанию 50).

Память в `compose.yml` поделена между сервисами в пределах лимита проекта (2 ГБ).
Упёрся сервис — его перезапустят, а администратору придёт уведомление.

## Ограничение частоты запросов

Traefik ограничивает любой сайт: около 200 запросов в секунду и 150 одновременных
с одного адреса. Сверх этого, в `compose.yml`, отдельный строгий лимит — 10 запросов
в минуту с адреса — стоит на то, что подбирают перебором или засыпают спамом:
- вход, регистрация, коды из писем и сброс пароля в API;
- вход в админку;
- отправка заявок и загрузка файлов модуля «Заявки». У загрузки свой роутер, а у роутера Traefik
  свой счётчик: файл — отдельный запрос, и пять файлов заявки не съедают попытки отправки и входа.
  Форма с пределом больше пяти файлов: шестой файл подряд получит 429, дальше — один файл в 6 секунд.

Отказ этого лимита (ответ 429) Traefik отдаёт с заголовками CORS для адресов из
`CORS_ALLOWED_ORIGINS` — фронт на другом домене покажет «Слишком много попыток», а не
«Нет связи с сервером». Предзапросы `OPTIONS` на эти адреса тоже отвечает Traefik, и лимит
они не тратят. Список адресов попадает в метки контейнера при создании: поменял
`CORS_ALLOWED_ORIGINS` — пересоздать контейнеры (`docker compose up -d --force-recreate`).

В приложении на этот случай есть и свой предохранитель: пять неверных попыток ввода
кода, и он сгорает.

Админку можно закрыть от всех, кроме адресов администраторов: добавить к роутеру
админки (в профиле full — сервиса `admin`) middleware инфраструктуры `admin-only@file`. Тогда и Swagger, и API
продолжат работать для всех — ограничение только на `/admin/`.

## Файлы

- `static/` — статика админки, собирается `collectstatic`, отдаётся контейнером `files`.
- `media/` — загруженные картинки и файлы, открытые всем по прямой ссылке.
- `private/` — файлы, которые наружу не отдаются: вложения заявок модуля «Заявки».
  В контейнер `files` эта папка не монтируется: файл отдаёт только бэкенд, проверив право, — из админки
  или автору заявки из API.

`media/` и `private/` лежат в папке проекта и попадают в её бэкап.

## Задачи по расписанию

Задачи по времени — уборку журнала, ничьих файлов форм и свои — запускает сервис `cron`.
Расписание — файл `project/crontab`, формат как у обычного cron, примеры строк — в самом файле.
Время московское: его задаёт строка `CRON_TZ` в файле, сам контейнер живёт по UTC. Уборка
в шаблоне — в 04:00 и 04:30. Файл — настройка проекта, как `settings.py`: удалили модуль —
уберите и его строку отсюда.

Новая задача — строка в `project/crontab` и push: расписание едет в образе, на сервер его привозит
выкладка. crontab на самом сервере для задач проекта не нужен: он не попадает в бэкап проекта,
не переезжает вместе с ним и пропадает, когда у человека забирают доступ к серверу.

- Что задачи вывели и чем закончились — `docker compose logs -f cron`.
- Задача не закончилась к следующему запуску — вторая копия не стартует, в логе предупреждение
  `not starting: job is still running`.
- Выкладка пересоздаёт контейнер `cron`, и задача, которая шла в этот момент, обрывается через
  секунду — иначе сайт не отвечал бы, пока она идёт. Долгая задача (выгрузка, импорт) должна
  спокойно переносить обрыв и повтор.

## Если что-то пошло не так

- **Контейнер перезапускается по кругу** — `docker compose logs --tail 100 app`.
  Обычно это `.env`: нет обязательной строки (её имя будет в логе).
- **Админка не пускает: «CSRF verification failed»** — в `CSRF_TRUSTED_ORIGINS` нет адреса
  сайта с `https://`.
- **Админка без стилей** — не собрана статика (`collectstatic`). Статика отвечает 403 —
  контейнер `files` запущен не под `1000:1000`: папка проекта видна только группам root,
  www-data (33) и 1000.
- **API отвечает 500 на всех эндпоинтах** — не та база или старый пароль: доступ в `.env`
  устарел (`DB_*` при `DEV=False`, `DEV_DB_*` при `DEV=True`). Обновить командой из
  «Первого запуска» и пересоздать контейнеры:
  `docker compose up -d --force-recreate` (`restart` новый `.env` не читает).
- **Сайт отвечает 404 от Traefik** — не совпадает `DOMAIN` в `.env` или контейнеры
  не поднялись: `docker compose ps`.
- **«Permission denied» при записи в `media/`, `private/`, `static/`** — папку создали руками
  без записи для группы: `chmod 2770 <папка>`. Код приложение менять не может — так задумано:
  он в образе и принадлежит root.
- **Новая версия не выложилась** — health-check сервера сообщит. Причина — в журнале
  автовыкладки (`sudo journalctl -u project-deploy@<проект> -n 50`), часто это миграция или
  `sync_async_models`; красное в CI видно на GitHub. Исправить и сделать push.
