# CLAUDE.md

Стек: **Django** (модели, миграции, админка) + **FastAPI** (API) + **Tortoise ORM** (асинхронный доступ к тем же таблицам).
Запросы делятся до Django: `/api/*` уходит в FastAPI, middleware Django в API не участвуют.

Структура и запуск — в [readme.md](readme.md). Перед работой над модулем — его `readme.md`:
там правила и подводные камни, которых по коду не видно.

## Рекомендации
- Все внешние HTTP-вызовы — с `timeout=60`: без таймаута запрос висит и блокирует воркер. В API — `aiohttp` (`httpx` под нагрузкой упирается в процессор), в командах и админке — `requests`/`httpx`.
- Критичное (БД, авторизация) — падаем сразу с понятной ошибкой. Некритичное (письмо, аналитика, уведомление) — `try/except`, warning в лог, основное действие продолжается.

## Команды
`manage.py` лежит в `app/`. Остальные команды — в [docs/commands.md](docs/commands.md).

Выполняй сам — они только пишут файлы, в базу не ходят:
- `python manage.py makemigrations` — создать файл миграции
- `python manage.py sync_async_models` — Tortoise-модели для API, после каждой правки
  моделей. Иначе код API пишется против устаревшей схемы. Миграцию он не заменяет
  и её отсутствие не покажет

Не выполняй, только покажи команду:
- `python manage.py migrate` — накат на базу подтверждает разработчик
- запуск и деплой: `runserver`, docker, `git push` (push в `dev` — выкладка dev-проекта),
  смена `DEPLOY_IMAGE` в `.env` сервера (выкладка сайта)

## Модели: Django → Tortoise
Схема одна, в `models.py`. API работает через Tortoise, Django ORM в API не используется.

- После правки моделей: `makemigrations` → `sync_async_models`. В git коммитятся и миграция, и `models_async.py`.
- Расширение Postgres (`pg_trgm`, `unaccent`…) — только миграцией (`TrigramExtension()`, `CreateExtension`), не руками в базе: поставленное руками есть только на проде. Почему и какие можно — [docs/commands.md](docs/commands.md), «Расширения Postgres».
- `models_async.py` руками не правится — генерируется.
- Все Tortoise-модели в одном приложении `models`: ссылка `"models.Product"`, имена моделей в проекте уникальны.
- В файле, где обе ORM (обычно `services.py`), — обе через модуль: `models.Page` и `models_async.Page`. По имени без префикса не видно, какая это ORM.
- Обратные связи называются как в Django: `category.product_set` или свой `related_name`.
- `on_delete` по умолчанию выполняет Django в Python, в базе правила нет — удаление из API записи со связанными упадёт. Нужно удалять из API — объявляй связь с `DB_CASCADE` / `DB_SET_NULL` / `DB_SET_DEFAULT`, тогда правило уходит в базу.
- Логику не класть в `save()` и сигналы: из API они не вызываются. Общее для админки и API — в `services.py`:
  - проверки и расчёты без базы — обычные функции, их зовут обе стороны;
  - простую правку данных админка делает сама, через Django;
  - действие с последствиями (письмо, остатки, история) и постановка задачи из админки — асинхронный сервис
    с `@with_sync`, из админки и команд — `.sync(id)`, передавать id, а не объект. Такое поле в админке только
    для чтения, меняется действием. Примеры вызова — [app/core/readme.md](app/core/readme.md#асинхронный-сервис-из-админки).
- Связи на модели вне проекта (`auth.Group`) в Tortoise — простой колонкой `group_id`.

## Структура модуля
Модуль — обычное Django-приложение из `INSTALLED_APPS`. `rest.py` подключается
автоматически — регистрировать роутер не нужно.

```
app/<module>/
├── apps.py          # verbose_name — раздел в админке и в Swagger
├── models.py        # Django-модели → миграции
├── admin.py         # админка
├── models_async.py  # Tortoise-модели — генерируются
├── schemas.py       # Pydantic-схемы запросов и ответов
├── services.py      # бизнес-логика
├── rest.py          # router = APIRouter() → /api/<module>/...
└── tests/           # тесты, хелперы в tests/create.py
```

`rest.py` — только эндпоинты: взять данные из запроса, вызвать валидацию, вызвать сервис, вернуть ответ. Логика в сервисах.

Фильтр списка в админке по связи с большим справочником — `AutocompleteFilter` из `core/admin_filters.py`
(`title`, `field_name`); у админки справочника нужны `search_fields`.

По мере разрастания — отдельными файлами:
- **conf.py** — настройки модуля: константы, из `.env` — только то, что у сайтов разное (ключи), с префиксом модуля
- **tasks.py** — фоновые задачи: `@broker.task` из `core.broker`, вызов `await task.kiq(...)`. Только здесь: воркер знает задачи из `tasks.py` модулей. Сюда — то, чей результат не нужен пользователю сразу (письма через `core/mailer.py`, отправка данных во внешние системы), и тяжёлое для процессора или базы (отчёты, выгрузки). Задача может выполниться повторно — повтор не должен вредить
- **validations.py** — только проверки: форматы, существование сущностей, права, расширения файлов. Возвращают валидные данные или `raise HTTPException`
- **client.py** — клиент внешнего API: авторизация, сессия, запросы с обработкой ошибок, `logger`. Возвращает `{"data": ..., "error": None}`
- **imports.py** — импорт из внешних источников и файлов. Возвращает `(created_count, updated_count)`
- **filters.py** — фильтры списков, если один набор используется в нескольких эндпоинтах
- **management/commands/** — только обёртка: разбор аргументов и вызов функции из `services.py` или `imports.py`

Общее для всех модулей — в `core`, см. [app/core/readme.md](app/core/readme.md).

## Нейминг
- snake_case, без сокращений: `is_medicine` (не `is_med`)
- Порядок: суть → уточнение → ограничение: `sum_fines_current`
- Bool — префикс `is_`, списки — суффикс `_list` (но поля и фильтры в единственном числе: `company_id`, не `company_ids`)
- Без предлогов: `TransactionsMedicine` (не `TransactionsForMedicine`)
- Одинаковые названия во всех представлениях
- Схемы: `XIn` — на вход, `XOut` — на выход

## Стандартные поля API
- `sort` — сортировка, префикс `-` для убывания. Допустимые поля перечислять в `description`
- `page`, `row` — пагинация
- `row_number` — порядковый номер, только в списках с пагинацией
- `items` — список записей
- `total` — итоги: `{count}`, либо `{count, sum}` для списков с суммами
- `{key}_from`, `{key}_to` — фильтры по диапазону
- `date_from`, `date_to` — по основной дате. Если `date_to` без времени — считать `23:59:59`
- `date_add_from` / `date_add_to`, `date_modified_from` / `date_modified_to` — по датам создания и изменения
- `search` — поиск по нескольким полям
- Связанные справочники (FK) — вложенным объектом `{entity}: {id, name}`, не разбивать на `_id` и `_name`. Основную сущность записи оставлять как `{entity}_id` на верхнем уровне

## API
- Только асинхронный код: эндпоинты и сервисы API — `async def`, база — Tortoise, внешние вызовы — `aiohttp`. Обычная `def`, Django ORM, `requests` в API — это производительность Django, а не FastAPI ([docs/benchmark.md](docs/benchmark.md)). Короткий расчёт на CPU (хеш пароля) — `asyncio.to_thread`
- Тяжёлое для процессора или базы в запросе не держать: расчёты на Python, отчёты, выгрузки, тяжёлый SQL — в `tasks.py`, пользователю — «готовится» и результат потом (или кэш). Внешний вызов, ответ которого пользователь ждёт сейчас, можно ждать прямо в эндпоинте через `aiohttp`: асинхронное ожидание процесс не занимает
- Справочники — в URL `/info`, списки — `/list`
- Списки с пагинацией — через `paginate()` и `sort_queryset()` из `core/pagination.py`, ответ `response_model=ListOut[XOut]`, в схеме нужно поле `row_number`. Короткий список без пагинации (справочник, сессии пользователя) — просто массивом
- Для полей с `_id` в списке — делать справочник с `id` и `name`
- В `description` эндпоинта писать документацию для Swagger: что делает, зачем нужен, фильтры и сортировка, ссылки на справочники, возможные ошибки

## Стиль кода
- Модели и схемы — компактно, в одну строку: `name = models.CharField("Название", max_length=200)`, `field: Type = Field(None, description="...")`
- Примеры в схемах — через `model_config = ConfigDict(json_schema_extra={"example": {...}})`
- Схемы не дублируют модели: это разные слои

## Обработка ошибок
Сообщения (`message`) — на русском.

- **422** — валидация Pydantic, обрабатывается автоматически: `{"message": "...", "full_error": [{"type", "loc", "msg"}]}`. Переводы — `core/translations.py`
- **422 у поля** — ошибку про поле нашёл сервис (занятый email, неверный код): `raise field_error({"email": "Текст"})` из `core/errors.py`, тот же формат — сайт покажет её под полем
- **401** — не авторизован или токен недействителен
- **403** — нет прав
- **404** — если не найдено и это не страшно, лучше пустой список или объект
- **406** — бизнес-логика не про поле, сообщение клиенту: `raise HTTPException(406, "Текст")`

## Тесты
Запуск — из `app/`: `python manage.py test --keepdb` (модуль — `python manage.py test form --keepdb`).
Нужен PostgreSQL, где пользователю из `.env` можно создать базу: Django заводит `test_<база>`.
Выполняй сам, если база в `.env` локальная (тестовая база своя, рабочую не трогает); если `.env`
смотрит на сервер через туннель — спроси: тесты создадут базу там.

- Тесты в `app/<module>/tests/`, файлы `test_{feature}.py`
- Хелперы создания объектов — в `tests/create.py`, название созвучно модели: `Company` → `create_company()`
- Хелперы переиспользуются между модулями, дефолты реалистичные — чтобы тест работал без лишних параметров.
  Связанный объект хелпер берёт из уже созданных, а нет — создаёт сам:
  `form_type = form_type or FormType.objects.first() or create_form_type()`. Тест передаёт только важное ему
- Тест API и всё, что ходит в базу через Tortoise (мост `.sync()`), — `ApiTestCase` из `core/tests/api.py`
  (или `TransactionTestCase`): Tortoise не видит незакоммиченного, а `TestCase` держит тест в транзакции.
  `self.api` — клиент FastAPI, `self.auth(user)` — заголовок с токеном, `self.wait_tasks()` — дождаться фоновых задач.
  Логика только на Django (админка, слаги) — обычный `TestCase`: он быстрее
- Тесты идут без Redis: задачи выполняются в процессе, письма — в `django.core.mail.outbox`
